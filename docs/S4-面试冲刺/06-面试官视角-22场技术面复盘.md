## 一、样本与结论

| 环节 | 数量 | 说明 |
|------|------|------|
| HR 初筛通过 | 30 份 | 3～6 年经验占绝大多数，比往期更年轻 |
| 技术面 | 22 场 | React / Vue 阵营各约一半 |
| 发出 offer | 3 个 | 通过率约 13.6% |
| 最终入职 | 2 位 | 学历、行业背景分布很广，与结果**无相关性** |

**三条结论：**

1. **不是人少，是符合要求的少。** 面了二十多人，真正觉得合适的只有两三个。缺的不是"投简历的人"，是"基础扎实 + 有项目深度"的人。

3. **真正卡人的五个点**：TS 类型能力、框架原理、浏览器原生 API 与工程化、CSS 基本功、项目深度。

> 💡 **给求职者的定心丸**：市场没有网传的那么差。AI 已经能写静态页面、调样式、做简单交互，被替代的是"只会写页面"的那一层；**基础扎实、有项目深度、学习能力强的人，手里能拿好几个 offer**。

## 三、面试现场的四类翻车现场

### 1️⃣ "框架党"的困境

框架用得特别溜，Hooks / Composition API 信手拈来，一离开框架就断线。

**面试官的杀手锏问题（答不上来的比例很高）：**

- 不用框架，用原生 JS 怎么实现一个响应式数据绑定？
- `document.querySelector` 和 `document.querySelectorAll` 返回的东西有什么区别？
- 数据变了 DOM 就变了，中间到底发生了什么？

**正解要点**：`Object.defineProperty`（Vue 2，逐个属性劫持 + 递归遍历 + 数组方法重写，新增属性需 `$set`）与 `Proxy`（Vue 3，代理整个对象 + 懒递归 + 13 种拦截 + 数组/新增属性天然支持），核心都是 **依赖收集（getter 里收集 effect）+ 派发更新（setter 里触发 effect）**。

> 🔁 **底层搞懂了，用什么框架都能快速上手；只学框架，换个版本就要从零开始。**

### 2️⃣ "背题选手"的翻车现场

回答特别流畅，流畅到不像在思考 —— 换个问法或追问一层，马上卡壳。

**典型场景**：问"什么是事件循环？"，宏任务微任务说得明明白白；追问"那 `requestAnimationFrame` 属于宏任务还是微任务？它和事件循环是什么关系？"—— 不知道。

**更危险的操作**：答不上来就反过来给面试官讲另一个知识点，试图把话题引到自己背过的内容上。**会就是会，不会就是不会，诚实比什么都强** —— 面试官对这个动作的识别率接近 100%。

> 📌 追问链的完整清单见本文 [第五节](#五面试官的追问链背过还是懂了一问就知道)，事件循环的完整答案见 [事件循环详解](#附录一事件循环追问链的完整答案)。

### 3️⃣ 手写题：通过率不到一半

题目并不偏：实现一个防抖节流、写一个深拷贝、封装一个通用请求函数。

| 表现 | 占比印象 | 面试官的判断 |
|------|---------|-------------|
| 逻辑漏洞一大堆（this 丢失、timer 未清、边界没处理） | 最多 | 基本功不过关 |
| 思路有，但写得磕磕绊绊 | 次之 | 练得少，但可培养 |
| "我平时都是用 lodash 的" | 不少 | ❌ 可以用库，但必须知道原理；**万一需要定制版本呢** |
| 一次性写对 + 主动说清边界 | < 50% | ✅ 这就是 offer 候选人 |

**面试官真正在看的不是"背出代码"，而是四件事**：边界处理（`this`/参数/立即执行/取消）、取舍说明（为什么这么写）、可维护性（命名与注释）、以及能不能讲清使用场景的区别（防抖 vs 节流 vs rAF 节流）。

### 4️⃣ 态度问题：一票否决

- 约的下午两点，两点十五没上线、发消息不回，两点半才急匆匆进来："忘了有面试"。
- 简历上写的项目自己说不清：做了多久、几个人做、自己负责哪块，说的和简历对不上。

> ⚠️ **态度决定一切。** 连面试都不认真对待，工作态度可想而知 —— 这类基本一票否决，与技术能力无关。

### 附录一：事件循环追问链的完整答案

**`requestAnimationFrame` 既不在宏任务队列，也不在微任务队列。** 它是浏览器**渲染管线**中的一个阶段：回调在 **每一帧渲染之前**（animation frame callbacks）执行，由屏幕刷新节奏（通常 60Hz ≈ 16.7ms）驱动。

```
一个宏任务 → 清空所有微任务 → 判断是否需要渲染
                            ├─ 是 → rAF 回调 → 样式计算/布局/绘制 → requestIdleCallback（空闲时）
                            └─ 否 → 取下一个宏任务
```

| 调度方式 | 归属 | 时机 |
|---------|------|------|
| `Promise.then` / `queueMicrotask` / `MutationObserver` | 微任务 | 当前宏任务结束后**立即清空** |
| `setTimeout` / `setInterval` / `MessageChannel` | 宏任务 | 下一轮事件循环（嵌套 5 层后最小 ~4ms） |
| `requestAnimationFrame` | 渲染前回调 | 下一帧绘制前，与刷新率对齐 |
| `requestIdleCallback` | 空闲回调 | 一帧渲染完成后的剩余时间，可能被饿死 |

**⚠️ 面试高频陷阱**：

```javascript
Promise.resolve().then(() => console.log('micro'))
requestAnimationFrame(() => console.log('rAF'))
setTimeout(() => console.log('timeout'), 0)

// ✅ 确定的：micro 一定早于 rAF
// ❌ 不确定的：rAF 与 timeout 谁先？——取决于定时器到期时刻与下一帧的时机，不能猜
```

答"rAF 一定在 setTimeout 后面"和"rAF 一定在前面"都是错的，**正确回答是"不保证，取决于帧时机"** —— 这正是"背题选手"翻车的经典点位。

另外两个加分点：

- **微任务饥饿**：递归 `queueMicrotask` 会让微任务队列永远清空不完，渲染被永久阻塞（页面卡死）。
- **Vue 曾用 `MessageChannel` 做宏任务降级**：`nextTick` 优先 `Promise`（微任务），不支持时降级 `setTimeout` / `setImmediate`，保证 DOM 更新后的回调时序。

完整版见 [事件循环详解](../../S1-基础夯实/JavaScript核心/05-垃圾回收事件循环与新特性.md) 与 [浏览器原理](../../S3-进阶提升/01-浏览器原理.md)。

### 附录二：`DeepReadonly` 的分层答案

```typescript
// L1：只会浅层（面试官：这才刚开始）
type Readonly1<T> = { readonly [K in keyof T]: T[K] }

// L2：会递归（大多数人停在这一层）
type Readonly2<T> = { readonly [K in keyof T]: T[K] extends object ? Readonly2<T[K]> : T[K] }

// L3：处理内置对象 + 数组/元组 + 函数（✅ 达标线）
type Primitive = string | number | boolean | bigint | symbol | null | undefined
type Builtin =
  | Primitive | Function | Date | RegExp
  | Map<any, any> | Set<any> | WeakMap<any, any> | WeakSet<any> | Promise<any>

type DeepReadonly<T> = T extends Builtin
  ? T
  : T extends ReadonlyArray<infer U>
    ? ReadonlyArray<DeepReadonly<U>>
    : T extends object
      ? { readonly [K in keyof T]: DeepReadonly<T[K]> }   // 同态映射，自动保留 ? 修饰符
      : T

// L4：加深度限制，防循环引用与递归爆炸（⭐ 加分项）
type DeepReadonlyN<T, D extends number = 8, Acc extends unknown[] = []> =
  Acc['length'] extends D
    ? T
    : T extends Builtin
      ? T
      : T extends ReadonlyArray<infer U>
        ? ReadonlyArray<DeepReadonlyN<U, D, [...Acc, unknown]>>
        : T extends object
          ? { readonly [K in keyof T]: DeepReadonlyN<T[K], D, [...Acc, unknown]> }
          : T
```

**必须能讲清的三个坑**：

1. **函数不能递归** —— 递归进函数会破坏参数逆变/返回值类型，直接 `T extends Function ? T` 短路。
2. **`Date` / `Map` / `Set` 要黑名单** —— 否则 `Date` 被映射成 `{}`，`getTime()` 全部消失。
3. **用 `keyof T` 的同态映射** —— 才能保留原有 `?` 可选修饰符；用 `[K in Exclude<keyof T, never>]` 等非同态写法会丢可选项。

配套题型（`DeepMutable` / `Awaited` / `Flatten` / `UnionToIntersection`）见 [TypeScript 高频题 · 类型体操进阶](../../S1-基础夯实/JavaScript核心/06-TypeScript高频题.md)。

- [ ] CSS 变量与 `@property`：为什么 `@property` 能做到普通变量做不到的过渡动画 —— L4

### ✅ 项目与软技能

- [ ] 挑一个项目，用 STAR 讲满 5 分钟且经得起三层追问 —— L3
- [ ] 能量化结果：首屏 ↓xx%、包体 ↓xx KB、QPS ↑xx%、故障 ↓xx% —— L3
- [ ] 讲清你在项目里"最难的一个技术决策"和"被否决的方案" —— L4

## 八、入职之后：新人最常被吐槽的三件事

面试官视角的另一面 —— 平时带新人时反复出现的共性问题，这些都是**可提前训练**的。

### 1️⃣ 代码规范意识弱

变量随便起名、函数又臭又长、注释基本没有。

**可执行的标准**：

- 命名：布尔用 `is/has/should` 前缀；函数用动词开头；常量全大写或 `kXxx`
- 长度：单个函数 ≤ 40 行、圈复杂度 ≤ 10，超了就拆
- 注释：**注释写"为什么"，不写"做了什么"**（代码本身就是"做了什么"）
- 边界：所有异步都要有失败分支；所有订阅都要有清理
- 工程化兜底：Lint + Format + 类型检查进 CI，不让规范靠自觉

> 💡 **代码是写给人看的。** 一个团队的代码质量，决定了这个团队能走多远。

### 2️⃣ 排错能力差（可练，且最值得练）

遇到 bug 就慌、只看报错最后一行、不会追堆栈、不会用 `console.log`、全靠瞎猜。

**一套 SOP（照着做就能超过大多数人）**：

```
1. 复现：先稳定复现，记录最小复现路径（不能复现 = 不能修）
2. 定位：从报错顶部读堆栈 → 找到自己代码的第一帧 → 打断点而不是打 log
3. 二分：注释/回滚/开关交替，用二分法把范围收敛到几十行
4. 假设：提出"我认为原因是 X"，然后设计实验证伪它
5. 归因：区分 数据问题 / 时序问题 / 环境问题 / 构建问题 / 浏览器兼容
6. 复盘：写清 根因 → 修复 → 如何更早发现（加日志？加监控？加测试？）
```

**必备工具**：断点与条件断点、`debugger`、Network 面板（ waterfall / 请求体 / 状态码）、Performance 面板、`source-map` 定位线上报错、错误监控（见 [前端监控与埋点](../../S3-进阶提升/06-前端监控与埋点.md)）。

### 3️⃣ 沟通协作能力有待提升

闷头干、有问题不说、deadline 到了才说做不完；描述问题半天讲不明白。

**三个立刻能用的模板**：

- **求助模板**：现象（截图/录屏）+ 已尝试的 3 种方法 + 我的判断 + 我卡在哪 + 预期什么时候有结论
- **风险上报模板**：风险点 + 影响范围 + 发生概率 + 备选方案 A/B + 需要谁在什么时间前决策
- **进度同步模板**：本週完成 / 下周计划 / 阻塞项 / 需要支持（每周固定一次，别等被问）

> 💡 前端是和产品、设计、后端打交道最多的岗位，沟通能力本身就是工程能力的一部分。
