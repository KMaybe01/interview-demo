#### 高频场景应答模板

##### 场景一：为什么自研表单引擎而非直接使用 @rjsf？

| 对比维度 | @rjsf | 自研 Schema 引擎 | 架构决策依据 |
|----------|-------|----------|-------------|
| 动态显隐逻辑 | 仅支持静态 visible 字段 | 运行时表达式 DSL（支持沙箱降级解析） | 核心网配置存在大量的复杂的跨节点逻辑判断 |
| 依赖联动算法 | 需要手写副作用处理 | 基于 DAG 拓扑排序 + 死循环环路检测 | 7 种网元参数依赖深度交织，手写极易死循环 |
| 实时 Schema 编辑 | 不支持 Schema/UI 双向流转 | 暴露 `setFormData` 与 AST 节点映射 | 测试人员需要实时调试与注入元数据 Schema |
| 体积与可扩展性 | Bundle 较重（~50KB），扩展局限 | 微内核架构，4 核心文件 + 业务注册表 | 保持零额外依赖，方便后续跨框架移植 |

##### 场景二：1000+ QPS 冲击下，如何保证 60fps 不丢帧？

> **架构逻辑**：
> 1. **瓶颈分析**：4000 msg/s 的高频推送导致 JavaScript 主线程频繁触发 `setState` / 脏检查，Reconciliation 开销压垮 Rendering，引发严重的 Frame Drop（丢帧率 47%）。
> 2. **背压设计**：在传输层插入 RxJS 管道，采用 `bufferTime(16ms, undefined, 64)` 进行时间/数量双重阀门限制。
> 3. **帧率对齐**：使用 `animationFrameScheduler` 将数据合并后的更新打包至浏览器的渲染帧（16.6ms）起点执行。
> 4. **结果**：每秒 4000 次 DOM/状态冲击被成功收敛为每秒 60 次批量更新，彻底消除渲染卡顿。

##### 场景三：十万级 GIS 点位渲染，为什么选择 Canvas 四重优化而不是直接切 WebGL？

> **技术决策思考**：
> 1. **渐进式演进视角**：WebGL 虽然上限高，但引入了着色器编写、上下文丢失处理、内存手动管理等额外复杂度。企业级项目应优先在现有技术栈（Canvas 2D）下发挥极限性能。
> 2. **四重策略削峰**：
     >    - **BBOX 视口裁剪**：只保留视口内 Feature，直接剔除 60%~70% 不可见点。
>    - ** Cluster 聚类**：将 40k 点聚类为 ~50 个特征点，从根本上降低绘制基数。
>    - **dataCache 全量缓存**：缩放平移时直接复用图层位图，零重复计算。
>    - **惰性刷新**：将高频 `mousemove` 节流为 `moveend` 渲染。
> 3. **扩展边界**：目前方案已将内存压至 30MB、帧率拉满 60fps。当点位进一步增长至 **百万级** 时，我预留了平滑迁移至 WebGL (Deck.gl/Mapbox GL) 的图层接口。

##### 场景四：Angular Signals 与 RxJS 在生产环境中如何协同？

> **选型范式**：** Signals 负责 UI 状态追踪，RxJS 负责异步事件流编排。**
>
> - **Signals 场景**：适合局部同步 UI 状态（如表格排序、选择集、表单字段值）。 Signals 提供自动依赖追踪与细粒度 DOM 更新，无需手动取消订阅（Unsubscribe），避免内存泄漏。
> - **RxJS 场景**：适合处理具有时间维度的复杂异步流（如 WebSocket 断线重连、多协议降级切换、输入框 Debounce 请求）。
> - **配合方式**：在 `@axyom-ui` 中，传输层采用 RxJS 进行事件流转换（`switchMap` / `retry`），最终将计算结果通过 `toSignal()` 转为 Signal 供视图层直连消费。
