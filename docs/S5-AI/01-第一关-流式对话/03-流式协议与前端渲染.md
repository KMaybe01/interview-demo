# 03 · 流式协议与前端渲染

> **一句话**：把"等 30 秒拿到一段话"变成"1 秒出第一个字"——并且中途能掐断、断了能重连。
>
> **前置**：[02-LLM调用与Token成本](./02-LLM调用与Token成本.md)
> **产出**：一个能处理分帧边界、支持中断、渲染多类型 parts 的流式前端
> **代码**：`apps/ai-course/server/handler.ts`、`apps/ai-course/src/stages/01-chat/ChatStage.tsx`

---

## 1. 原理（够用即可）

### 为什么是 SSE 而不是 WebSocket

| 方案 | 特点 | 适合 |
|---|---|---|
| **轮询** | 实现简单，延迟高、浪费请求 | 几乎不适合 LLM |
| **SSE** | 单向（服务端→客户端）、基于 HTTP、天然重连、可被 CDN/代理理解 | **LLM 生成（单向流）** |
| **WebSocket** | 双向、需独立协议与网关支持 | 实时语音、协作编辑等双向场景 |

LLM 生成是**单向推送**，用 SSE 就够了，还能白拿 HTTP 生态（缓存、压缩、代理、鉴权）。

### SSE 帧长什么样

```
data: {"type":"text-delta","id":"txt-0","delta":"你"}

```
- 一个**事件**以空行 `\n\n` 结束
- `data:` 后可以跟任意 JSON（本仓库 Go 侧用 `event: <type>\ndata: <json>\n\n`）
- 结束时服务端发 `data: [DONE]`（AI SDK 的 UI Message Stream 约定）

### AI SDK 的 UI Message Stream 事件（前端要认得的）

`start` → `start-step` → `text-start` → `text-delta`… → `text-end` → `finish-step` → `finish`（带 `messageMetadata`）→ `[DONE]`

## 2. 企业实现要点

### ① TCP 分帧边界：一个 `data:` 可能拆成多个 chunk

这是新手最常踩的坑：网络层不保证一个 SSE 事件落在一个 TCP 包里。必须**按 `\n\n` 缓冲后再解析**，不能按行读。

本仓库 `apps/ai-demo/src/services/aiStream.ts` 就是手写解析器的范例：累积 buffer → 找 `\n\n` → 切出一个完整事件 → 剩余部分留到下一轮。

> 用 AI SDK 的 `DefaultChatTransport` 时这层已经帮你做好了；但**知道它存在**，面试才有东西可说。

### ② 代理缓冲会让你的流变成"假流"

Nginx / 网关默认可能缓冲响应，导致前端 30 秒后一次性收到全部内容。排查顺序：

```nginx
X-Accel-Buffering: no;
proxy_buffering off;
proxy_cache off;
```
AI SDK 的 `UI_MESSAGE_STREAM_HEADERS` 已经带上了 `x-accel-buffering: no` 等头，遇到"本地流式正常、上线后不流式"，先查这个。

### ③ 心跳与断线

- 本仓库 Go 侧每 **15 秒**发一次心跳（`internal/airouter/handler.go`），防止中间层因空闲断开
- 客户端断线后应该能**重连并续传**：AI SDK 支持 `resume`（流式中断后从断点继续）

### ④ 中断必须传到服务端

用户点"停止"或关页面时，前端 abort 只是**不再接收**，服务端还在算、还在计费。必须：

```ts
// apps/ai-course/server/handler.ts
const controller = new AbortController();
req.on('close', () => controller.abort());   // 连接断开 → 中止生成
```

### ⑤ 渲染必须遍历 `parts`

```tsx
{message.parts.map((part) => {
  if (part.type === 'text') return <div>{part.text}</div>;
  if (part.type === 'tool-call') return <ToolCard {...part} />;  // 后面的关卡会补
  ...
})}
```

只渲染 `message.content` 会丢掉工具调用、推理过程与引用来源——**这是 AI SDK v7 最常见的迁移事故**。

## 3. 代码实现

服务端：把模型输出转成 UI Message Stream 并 pipe 到 Node 响应：

```ts
const result = streamText({ model, messages, abortSignal: controller.signal });
const stream = toUIMessageStream({ stream: result.stream, messageMetadata: ({ part }) => ... });
await pipeUIMessageStreamToResponse({ response: res, stream });
```

前端：`status` 三态驱动 UI，`stop()` 中断：

```tsx
const { messages, sendMessage, stop, status } = useChat({ transport });
const isBusy = status === 'submitted' || status === 'streaming';

{status === 'submitted' && <div>正在等待首个 token…</div>}
{isBusy && <button onClick={() => stop()}>停止生成</button>}
```

## 4. 验证与观测

```bash
# 关键：加 -N 禁用 curl 自己的缓冲，否则你会以为没流式
curl -N -X POST http://localhost:5199/api/chat \
  -H 'content-type: application/json' \
  -d '{"messages":[{"id":"1","role":"user","parts":[{"type":"text","text":"讲个笑话"}]}]}'
```

| 观测点 | 怎么看 | 达标 |
|---|---|---|
| **TTFT** | 从回车到第一个 `text-delta` 的时间 | < 1s（本地模型/弱网放宽） |
| **是否真流式** | 帧是否**逐批**到达，而不是最后一次性 | 逐批到达 |
| **中断是否生效** | 中途 Ctrl-C，看服务端日志是否停止输出 | 立即停止 |
| **parts 是否完整** | 工具调用消息里能否看到 `tool-call` part | 能看到（第三关验证） |

## 5. 面试追问

> **Q：SSE 和 WebSocket 到底怎么选？**
> 看方向。LLM 生成是单向 → SSE；需要客户端持续上行（语音、实时协作）→ WebSocket。SSE 还自带断线重连，且能复用 HTTP 网关。

> **Q：为什么前端收流要自己做缓冲？**
> TCP 不保留消息边界，一个 SSE 事件可能被拆到多个 chunk。按行解析会拿到半个 JSON。

> **Q：用户点了停止，服务端还在烧钱吗？**
> 如果只 abort 前端请求 → 在烧。必须把 abort 传到模型调用（监听 `req.on('close')` + `AbortController`）。

> **Q：上线后流式变成"转圈 30 秒"，怎么排查？**
> 先看是不是代理缓冲（Nginx `proxy_buffering` / 响应头 `X-Accel-Buffering`），再看是不是某个中间层把 SSE 降级成了普通 HTTP。

> **Q：`message.content` 和 `message.parts` 什么关系？**
> parts 是结构化内容数组（text / reasoning / tool-call / source…），`content` 只是文本摘要。v7 起必须按 parts 渲染。
