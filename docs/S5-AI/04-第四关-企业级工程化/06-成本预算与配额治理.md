# 06 · 成本预算与配额治理

> **一句话**：AI 应用的账单是**按次累积**的，没有预算和配额，一个循环调用的 Agent 就能烧掉一个月预算。
>
> **前置**：[01-多Provider网关与熔断降级](./01-多Provider网关与熔断降级.md)
> **产出**：三层成本控制——模型分层、缓存复用、用户/会话级配额
> **代码**：`apps/ai-course/shared/cost.ts`、`server/models.ts`；后端参考 `apps/backend/internal/llm/pricing.go`

---

## 1. 原理（够用即可）

成本公式（把"感觉很贵"变成"算得出来"）：

```
单次成本 = (输入token / 1e6 × 输入单价) + (输出token / 1e6 × 输出单价)
月成本   = DAU × 平均会话数 × 平均轮次 × 单次成本 × 30
           × (1 + 重试率) ÷ 缓存命中折扣
```

三个放大器，最容易被忽略：

| 放大器 | 说明 |
|---|---|
| **上下文累积** | 第 N 轮的输入 = 前 N-1 轮 + 本轮，是**平方级**增长 |
| **Agent 循环** | 一次用户请求可能触发 5-20 次模型调用 |
| **失败重试** | 重试成功的请求，失败的那些也计费 |

## 2. 企业实现要点

### 第一层：模型分层（省 70%+）

| 请求类型 | 档位 | 思路 |
|---|---|---|
| 意图识别、改写、分类、简单问答 | 快速档 | 用便宜模型覆盖 70% 请求 |
| 复杂推理、长文档、代码生成 | 旗舰档 | 快速档置信度低时再升级 |

升级策略：**快速档先答，置信度低/检测到困难特征时再用旗舰档重答**（比一律用旗舰便宜得多）。
本教程 `models.ts` 就是 `fast` / `smart` 两档，档位由请求体传入，前端可切换。

### 第二层：缓存（省 30-50% 输入）

| 缓存类型 | 命中对象 | 说明 |
|---|---|---|
| **Prompt Caching** | 系统提示 + 固定前缀 | 前缀不变才能命中，所以**稳定内容放前面、动态内容放后面** |
| **语义缓存** | 相似问题 | 命中直接返回历史答案，注意时效与个性化 |
| **检索缓存** | 相同 query 的召回结果 | 知识库更新前可复用 |

本仓库 Go 侧在 Run 统计里记录了 `CacheHit` 字段，就是用来观察这一层效果。

### 第三层：配额（防止失控）

| 粒度 | 用法 |
|---|---|
| 用户级 | 每日/每月 token 上限 |
| 会话级 | 单会话最大轮次、最大总 token |
| 请求级 | `maxOutputTokens` 上限 |
| Agent 级 | 最大步数（本仓库 `MaxSteps = 5`）、单轮最大工具调用数（`MaxToolCallsPerStep = 4`） |
| 全局 | 熔断期成本上限、预算告警阈值 |

> Agent 场景里**步数与工具调用上限是硬性安全边界**，不只是省钱——它是防止死循环的第一道闸（见第三关）。

### 定价数据怎么管

`apps/backend/internal/llm/pricing.go` 的做法值得照抄：

- 单位：**美元 / 1M token**
- 命中策略：精确 → **前缀模糊匹配** → 兜底价 `{0.15, 0.6}`
- 兜底时置 **`Estimated = true`**，把"这是估算"这件事显式传给上游

> 这条 `Estimated` 字段是本仓库做得特别好的一个细节：**报价和估算必须可区分**，否则你拿估算值去对账就会出事。

## 3. 代码实现

教程侧把换算做成纯函数并配了单测：

```ts
// apps/ai-course/shared/cost.ts
export const SAMPLE_PRICING = {
  fast:  { input: 0.25, output: 2 },     // ⚠️ 教学示例值，不是厂商报价
  smart: { input: 2.5,  output: 10 },
  offline: { input: 0, output: 0 },
};

export function estimateCost(usage: TokenUsage, tier: ModelTier): CostBreakdown;
```

配合 `messageMetadata` 下发到前端，做到**每条消息都能看见花了多少钱**：

```ts
cost: estimateCost(part.totalUsage, entry.tier)
```

UI 上把累计成本放到显眼位置——成本可见会直接改变用户行为（这是最便宜的优化手段）。

## 4. 验证与观测

| 观测项 | 位置 |
|---|---|
| 单次成本 | 消息下方的 `cost` 徽标 |
| 会话累计 | 前端累加 `message.metadata.usage` |
| 档位分布 | trace 里记录 `tier`，统计快慢档占比 |
| 缓存命中率 | Run 的 `CacheHit` 字段 |
| 降级率 | `degraded` 标记占比 |

验收标准：

- [ ] 每条 AI 回复都能显示本次 token 数与估算成本
- [ ] 能按档位统计成本分布，知道钱花在哪一档
- [ ] 有输出上限与 Agent 步数上限
- [ ] 明确区分"真实价"与"估算价"

## 5. 面试追问

> **Q：怎么给一个 AI 功能做成本预算？**
> 拆四个量：DAU × 会话数 × 轮次 × 单次 token；再乘单价，加重试率，减缓存折扣。要注意上下文累积是平方级增长。

> **Q：最有效的降本手段是什么？**
> 排序：模型分层（最大头）→ 减上下文（裁剪历史、摘要）→ 缓存 → 限制输出长度。换便宜模型通常比优化 Prompt 省得多。

> **Q：Prompt Caching 为什么要求"前缀稳定"？**
> 缓存按前缀匹配，前缀一变整段失效。所以系统提示、工具定义、固定示例放前面，用户输入和时间戳放最后。

> **Q：Agent 为什么必须限步数？**
> 既是成本也是安全：死循环会持续烧钱并可能反复触发副作用工具。本仓库 `MaxSteps=5`、`MaxToolCallsPerStep=4`。

> **Q：估算价和真实价怎么区分？**
> 用显式字段（本仓库 `Estimated=true`），并在 UI/账单里区分展示。混在一起会导致对账错误和信任问题。
