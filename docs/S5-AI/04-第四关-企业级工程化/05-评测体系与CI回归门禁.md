# 05 · 评测体系与 CI 回归门禁

> **一句话**：改 Prompt、换模型这件事，应该像改代码一样有测试保护。
>
> **前置**：[02-第二关 · RAG 评测闭环](../02-第二关-知识增强RAG/04-RAG评测闭环.md)
> **产出**：一个能在 CI 里跑的评测任务 + 一条"分数下降就失败"的门禁
> **代码**：后端参考 `apps/backend/internal/obs/eval.go`、`apps/backend/internal/obs/prompt.go`

---

## 1. 原理（够用即可）

AI 应用的"回归"和传统软件不一样：代码没变，**行为**会变。

| 变更 | 可能的影响 |
|---|---|
| 改 Prompt | 语气变了 / 拒答率变了 / 忠实度下降 |
| 换模型版本 | 输出格式漂移、指令遵循能力变化 |
| 调温度 / 档位 | 稳定性与创造性此消彼长 |
| 改分块 / 检索 | 召回率变化，进而影响答案质量 |

所以要把"行为"变成**可重复测量的分数**，并钉在 CI 上。

---

## 2. 企业实现要点

### 后端参考实现：`apps/backend/internal/obs/eval.go`

| 项 | 实现 |
|---|---|
| 四指标 | RetrievalHit（overlap ≥ **0.3**）、Faithfulness、AnswerRelevancy、ContextPrecision（单块 overlap > **0.15**） |
| 阈值 | `FaithfulnessFail = 0.7`、`RelevancyWarn = 0.5`、`MinRetrievalHitRate = 0.6`，任一告警即 `Failed` |
| 运行 | `POST /api/ai/eval/run`，默认 topK 3，保留最近 **50** 次结果 |
| 数据集 | `GET/POST /api/ai/eval/datasets` |

> ⚠️ 诚实边界：这四个分数是**词典重合度代理值**（中文按单字切），源码注释明确写出"0.5 的余弦重合 ≠ 0.8 的人工判定"。
> 正确用法：**看趋势、做门禁**；对外汇报质量要换语义级评测或人工抽检。

### Prompt 版本管理：`apps/backend/internal/obs/prompt.go`

把 Prompt 当**代码资产**管理，这是评测闭环的前提：

| 能力 | 实现 |
|---|---|
| 版本 | `Create` 的版本号 = `len(history) + 1`，**首个版本自动激活** |
| 激活/回滚 | `Activate(name, version)` 互斥激活 → **回滚 = 激活旧版本** |
| 渲染 | `RenderActive` 返回 `(text, version)`；变量缺失直接报错（避免静默输出乱码模板） |
| 内置 | `EnsureDefaults` 提供 `rag.answer` / `chat.system` / `agent.react` |

**没有版本化的 Prompt，就没有可回滚的发布**——一次坏改动只能靠记忆回滚。

### 门禁怎么配

```
PR 改动 Prompt / 模型 / 检索参数
      ↓
CI 跑评测集（固定数据集 + 固定 topK）
      ↓
与基线对比：Faithfulness / Relevancy / RetrievalHitRate
      ↓
低于阈值 或 相对跌幅 > 5%  →  PR 失败，展示逐条 diff
```

两个细节：
1. **数据集要版本化**，否则不同时间的分数不可比；
2. **分数要能下钻到单条**，否则没人愿意查为什么挂了。

## 3. 代码实现

最小闭环的形态：

```ts
interface EvalRun {
  id: string;
  datasetVersion: string;
  promptVersion: number;      // 与 Prompt 版本强绑定，才能定位"是哪次改动导致的"
  modelTier: ModelTier;
  metrics: { retrievalHitRate: number; faithfulness: number; relevancy: number; contextPrecision: number };
  failed: boolean;
  cases: Array<{ question: string; hit: boolean; score: number }>;
}
```

在 CI 里就是一条命令 + 一次阈值断言：

```bash
bun run --cwd apps/ai-course eval          # 跑评测集，输出 JSON
# CI 里断言：metrics.faithfulness >= 0.7 && metrics.retrievalHitRate >= 0.6
```

## 4. 验证与观测

| 动作 | 期望 |
|---|---|
| 跑一次基线 | 得到四个指标并落库 |
| 故意把 Prompt 改坏 | 分数下降、CI 失败、能看到逐条明细 |
| 激活旧版本 Prompt | 分数回到基线（验证回滚有效） |
| 换模型档位后重跑 | 得到"档位 × 质量 × 成本"的对照表 |

验收标准：

- [ ] 评测集与 Prompt 版本都进了版本管理
- [ ] 一次命令可跑，输出机器可读的 JSON
- [ ] CI 有阈值断言，失败时能看到 diff
- [ ] 明确知道当前指标是**代理值**，不作为对外质量承诺

## 5. 面试追问

> **Q：为什么 AI 项目特别需要 CI 评测？**
> 因为行为变更的来源是"自然语言和配置"，而不是代码 diff，Code Review 看不出来。只有跑分数才知道有没有退化。

> **Q：评测集怎么维护？**
> 版本化存放；每次 Prompt 或模型变更都要重跑；线上出现 bad case 就补进数据集（它就是你的回归用例）。

> **Q：分数波动很大怎么办？**
> 先固定温度（评测用低温，如 0-0.3）、固定档位、固定 topK；仍不稳定就多次运行取均值，或改判相对跌幅而非绝对值。

> **Q：Prompt 怎么做灰度？**
> 与代码灰度同构：影子流量 → 1% → 10% → 全量，每个版本都能一键回滚（激活旧版本号）。

> **Q：代理指标（词典重合度）够不够？**
> 做门禁够（便宜、可离线、可重复）；做质量对外承诺不够，需要语义级评测（RAGAS/模型打分）或人工抽检做校准。
