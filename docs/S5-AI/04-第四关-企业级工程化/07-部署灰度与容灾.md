# 07 · 部署灰度与容灾

> **一句话**：AI 应用的发布是"行为发布"，不是"代码发布"——灰度的是 Prompt 和模型，回滚的是版本而非代码。
>
> **前置**：[05-评测体系与 CI 回归门禁](./05-评测体系与CI回归门禁.md)
> **产出**：一条"影子 → 1% → 10% → 全量"的发布流水线，以及一份可执行的容灾清单
> **代码**：后端参考 `apps/backend/internal/obs/prompt.go`、`apps/backend/internal/llm/resilience.go`

---

## 1. 原理（够用即可）

传统发布回滚的是**二进制**；AI 发布要能回滚三样东西：

| 可回滚项 | 版本载体 | 回滚方式 |
|---|---|---|
| 代码 | git tag / 镜像 | 重新部署 |
| **Prompt** | 版本号 | 激活旧版本（本仓库 `Activate(name, oldVersion)`） |
| **模型** | 档位 + 型号 | 改注册表配置（型号放 env，见第一关） |

把后两者纳入发布流程，是 AI 应用与传统应用最大的运维差异。

---

## 2. 企业实现要点

### 灰度四步

| 阶段 | 做法 | 观察什么 |
|---|---|---|
| **影子流量** | 新 Prompt/模型只跑不返回 | 与线上结果做 diff，看质量与成本 |
| **1%** | 真实放量，只看核心指标 | 错误率、拒答率、TTFT |
| **10%** | 扩大 | 用户反馈、成本曲线 |
| **全量** | — | 保持监控 24h |

每个阶段都要有**明确的一键回滚点**：Prompt 版本号 + 模型档位。

### Prompt 版本化是回滚的前提

`apps/backend/internal/obs/prompt.go` 的设计：

- `Create` 版本号 = `len(history) + 1`，首个版本**自动激活**
- `Activate(name, version)` **互斥激活** → 回滚就是"激活旧版本号"
- `RenderActive` 返回 `(text, version)`，**变量缺失直接报错**（防止模板变量拼错后静默输出乱码）
- 内置 `rag.answer` / `chat.system` / `agent.react` 三套默认 Prompt

实践要点：**把每次回答使用的 Prompt 版本号记进 trace**。否则线上出问题时，你不知道用户是被哪个版本的 Prompt 影响的。

### 容灾清单（照着做一遍）

| 层 | 措施 | 本仓库实现 |
|---|---|---|
| 模型层 | 主备 + 熔断 + 离线兜底 | `ExecuteWithFallback` → `Offline()`（`finishReason="degraded"`） |
| 检索层 | 检索失败不阻塞生成 | 检索异常降级为空上下文继续回答 |
| 工具层 | 失败重试 + 超时 + 审批 | `MaxSteps=5`、`MaxToolCallsPerStep=4`、L2 操作走 HITL |
| 网关层 | 限流 + 配额 | 见成本章节 |
| 数据层 | trace/审计限长、TTL | Recorder runCap 2000、traceTTL 30min、审计环形 500 条 |
| 展示层 | **降级态显式可见** | 前端据 `degraded` 显示"降级模式" |

### 流式场景的两个额外注意点

1. **心跳**：长连接要发心跳（本仓库每 **15 秒**一次），否则中间层会判空闲断开
2. **代理缓冲**：上线后"不流式"多半是 Nginx `proxy_buffering` 或缺失 `X-Accel-Buffering: no`

## 3. 代码实现

发布与回滚的最小动作就是两个接口：

```bash
# 灰度：激活某个 Prompt 版本
curl -X POST http://localhost:8080/api/ai/prompts/chat.system/activate -d '{"version":7}'

# 回滚：激活上一个版本
curl -X POST http://localhost:8080/api/ai/prompts/chat.system/activate -d '{"version":6}'
```

教程侧的配套动作（第一关已具备）：

```bash
# 只改环境变量就换型号 —— 不改业务代码
AI_COURSE_MODEL_FAST=gpt-5-mini bun run --cwd apps/ai-course dev
```

关键纪律：**型号和 Prompt 版本都要能被一条命令改回去**，并且改动要留痕（版本号 + 谁改的 + 什么时候）。

## 4. 验证与观测

| 演练 | 期望 |
|---|---|
| Prompt 灰度 | 影子阶段能拿到新旧 diff；激活新版本后 trace 里记录新版本号 |
| Prompt 回滚 | 激活旧版本号后行为立即恢复 |
| 模型宕机 | 自动切备用；再不行进降级态并显式提示 |
| 断网 | 返回 `degraded`，前端显示降级标记 |
| 长时间流式 | 15s 心跳不断开；中间层不缓冲 |

可观测配套：`degraded_responses_total`、`circuit_state{provider}`、按 Prompt 版本分组的质量指标。

## 5. 面试追问

> **Q：AI 应用发布为什么要先跑影子流量？**
> 因为 Prompt/模型的变更无法靠 Code Review 判断影响，只有用真实流量跑一遍对比，才知道质量和成本的变化。

> **Q：怎么做到"一键回滚"？**
> Prompt 版本化 + 互斥激活（回滚 = 激活旧版本号）；型号放环境变量（回滚 = 改配置）。两者都要留痕。

> **Q：降级态为什么要让用户看见？**
> 降级回答和正常回答外观一样，不标注就等于欺骗用户。显式标记既是对用户诚实，也让你能统计降级率。

> **Q：灰度期间看哪些指标？**
> 三层：稳定性（错误率、TTFT、降级率）、质量（评测分/拒答率/用户反馈）、成本（单次成本、档位分布）。

> **Q：限长和 TTL 为什么也算容灾？**
> 内存无界的 trace/审计会让进程 OOM，这也是一种"挂"。本仓库 audit 环形 500 条、字段截断 200/500 字符、trace TTL 30min，都是在为内存兜底。
