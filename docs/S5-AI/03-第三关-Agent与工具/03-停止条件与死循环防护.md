# 03 · 停止条件与死循环防护

> **一句话**：Agent 最大的风险不是"答错"，而是"停不下来"——一个循环就是一份停不下来的账单和一堆重复副作用。
>
> **前置**：[02-工具设计契约](./02-工具设计契约.md)
> **产出**：一组可验证的收敛手段（步数/预算/重复检测/超时），以及"停下来之后怎么办"
> **代码**：`apps/ai-course/server/agent.ts`；后端参考 `apps/backend/internal/airouter/stream.go`

---

## 1. 原理（够用即可）

Agent 循环是 `推理 → 调工具 → 喂回结果 → 再推理` 的迭代。它天然可能不收敛：

- 工具一直报错，模型一直重试
- 模型认为"还没查全"，反复检索
- 两个工具互相把结果推给对方

所以必须有**外部强制的停止条件**，不能指望模型自己说"我好了"。

---

## 2. 企业实现要点

### 四道闸（本仓库的默认值）

| 闸 | 默认值 | 位置 |
|---|---|---|
| **最大步数** | `MaxSteps = 5` | `apps/backend/internal/airouter/stream.go` |
| **单轮最大工具调用数** | `MaxToolCallsPerStep = 4` | 同上 |
| **审批中断** | 遇 HITL 时 `finishReason = "awaiting_approval"`，**循环直接中断** | 同上 |
| **超时** | 非流式 45s；流式靠中断 | `apps/backend/internal/llm/openai_compat.go` |

注意审批那条：**它不是"等待"，而是中断**。前端拿到 `awaiting_approval` 后，要把已批准的 `toolCallId` 放进 `approvedToolCalls` **重发整个请求**——即"重试"发生在客户端，服务端不保留挂起状态（这也和 MCP 的无状态化一致）。

### 重复检测：最容易被漏掉的一道

步数上限防的是"跑太久"，防不住"原地打转"。要额外检测：

| 信号 | 含义 |
|---|---|
| 同一工具 + 同一参数被调用 ≥ 2 次 | 模型在原地打转 |
| 连续 N 步输出长度趋近 0 | 卡住了 |
| token 消耗超过预算 | 成本失控 |

检测到之后**不要静默重试**，应该：停下来 → 把已获得的信息总结给用户 → 说明卡在哪一步。

### 停下来之后怎么办

| 情况 | 处理 |
|---|---|
| 达到步数上限 | 用已有信息作答，并说明"未完全完成，卡在第 N 步" |
| 工具持续报错 | 换工具 / 降级为不使用工具直接回答 |
| 需要澄清 | 进入 `input-required`，问用户 |
| 预算用尽 | 明确告知并停止（**不要偷偷降质量继续跑**） |

> 原则：**失败的 Agent 也要给用户一个可理解的交付**，而不是"请求失败"。

## 3. 代码实现

```ts
// apps/ai-course/server/agent.ts
const MAX_STEPS = 5;
const MAX_TOOL_CALLS_PER_STEP = 4;

for (let step = 1; step <= MAX_STEPS; step += 1) {
  const calls = plan(...);                       // 模型决定这一步调什么
  if (calls.length === 0) break;                 // 模型说不用调了 → 收敛

  if (calls.length > MAX_TOOL_CALLS_PER_STEP) return stop('too_many_calls');
  if (seen.has(signature(calls))) return stop('repeated_call');   // 重复检测
  seen.add(signature(calls));

  const blocked = calls.filter((c) => needsApproval(c));
  if (blocked.length > 0) return awaitingApproval(blocked);       // 中断，不是等待
  ...
}
return stop('max_steps');
```

关键点是 `signature(toolName + args)` 的重复检测——它防的是"步数没超但一直在原地"的情况。

## 4. 验证与观测

| 场景 | 怎么造 | 期望 |
|---|---|---|
| 正常收敛 | 一步就能答的问题 | 循环自然结束 |
| 步数上限 | 让它反复调工具 | 第 5 步后停止并给出已完成部分 |
| 重复调用 | 同一工具同一参数 | 第二次就被检测并停止 |
| 审批中断 | 调 L2 工具 | 返回 `awaiting_approval`，不产生副作用 |
| 预算用尽 | 设很小预算 | 明确告知后停止 |

观测指标：**步数分布**（P50/P95）、停止原因分布（`converged` / `max_steps` / `repeated` / `awaiting_approval`）、单次会话成本。
停止原因必须可统计——否则你不知道系统里有多少是"跑崩了"而不是"完成了"。

## 5. 面试追问

> **Q：怎么防止 Agent 死循环？**
> 多层：最大步数、单步工具数上限、重复调用检测（同工具同参数）、token 预算、超时。步数上限防"跑太久"，重复检测防"原地打转"，两者缺一不可。

> **Q：达到步数上限后应该怎么办？**
> 不要报"失败"。用已获得的信息总结作答，并明确说明未完成到哪一步、卡在哪。用户体验上，"部分结果 + 说明"远好于"错误"。

> **Q：为什么审批要做成"中断 + 重发"，而不是服务端挂起等待？**
> 挂起意味着服务端要保留会话状态（连接、内存、超时），既难扩容又难恢复；中断 + 客户端重发让服务端保持无状态，也与 MCP 2026-07-28 的无状态化方向一致。

> **Q：重发时怎么避免重复执行已经做过的工具？**
> 用 `approvedToolCalls` 精确指定本次放行哪些调用，且工具侧有幂等键。两者配合才安全。

> **Q：为什么统计"停止原因分布"很重要？**
> 因为"完成"和"跑崩"在用户侧可能都表现为"给了个答案"。不统计停止原因，你永远不知道有多少请求是失败的。
