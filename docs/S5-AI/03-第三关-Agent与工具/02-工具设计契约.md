# 02 · 工具设计契约

> **一句话**：模型决定"调不调"，工具契约决定"调了会怎样"——Agent 的事故几乎都不是模型笨，而是工具设计没有边界。
>
> **前置**：[01-Agent设计模式](./01-Agent设计模式.md)
> **产出**：一组带副作用分级、幂等键、超时与审计的工具，并能在 UI 上看到"谁被拦下了"
> **代码**：`apps/ai-course/server/tools.ts`；后端参考 `apps/backend/internal/tool/`

---

## 1. 原理（够用即可）

一次工具调用要回答五个问题，缺一个就是隐患：

| 问题 | 契约项 |
|---|---|
| 干什么？ | `name` + `description`（模型靠它决定要不要调） |
| 传什么？ | `parameters`（JSON Schema） |
| 有多危险？ | **副作用等级** |
| 能重试吗？ | **幂等键** |
| 卡住怎么办？ | **超时** |

---

## 2. 企业实现要点

### 副作用分级（最重要的一条）

| 等级 | 含义 | 策略 |
|---|---|---|
| **L0 只读** | 查询、检索、计算 | 自动执行 |
| **L1 可撤销写** | 创建草稿、发站内通知 | 自动执行 + 可回滚入口 |
| **L2 不可逆写** | 转账、发邮件、删数据、下订单 | **必须人工审批** |

本仓库的默认值是 `DefaultTier = LevelConfirm`（`apps/backend/internal/airouter/service.go:52`）——**默认要确认，显式放开才自动执行**，这个默认值方向是对的。

### 三条铁律

| 铁律 | 违反后果 | 实现要点 |
|---|---|---|
| **幂等** | 重试 = 重复扣款 / 重复发邮件 | 写操作必须有幂等键；同一键重复调用返回首次结果 |
| **有界** | 一个慢工具拖死整个 Agent 循环 | 声明超时；超时返回**结构化超时结果**（不是抛异常让上层猜） |
| **分级** | 要么全拦（难用）要么不拦（不敢上线） | 只对 L2 走审批，L0 全放行 |

### 审计：把"谁做了什么"留下来

`apps/backend/internal/tool/audit.go` 的 `Outcome` 字段设计得很好，它直接对应"哪一层防线起了作用"：

| Outcome | 含义 |
|---|---|
| `success` / `failure` | 正常 / 报错 |
| `blocked_permission` | 权限分级拦下（L2 未审批） |
| `blocked_injection` | 沙箱判定为注入 |
| `blocked_rate_limit` | 限流 |

两个工程细节值得抄：
1. **环形缓冲上限 500 条**——内存里的审计必须是"最近可排查量"，不能无界增长；
2. **字段截断**（`Args` 200 字符、`Detail` 500 字符）——一条大 payload 就能撑爆内存。

## 3. 代码实现

```ts
// apps/ai-course/server/tools.ts
export type ToolLevel = 'L0' | 'L1' | 'L2';

export interface AgentTool {
  name: string;
  description: string;
  parameters: Record<string, unknown>;
  level: ToolLevel;                 // 副作用等级 —— 决定要不要审批
  timeoutMs: number;                // 超时上限
  idempotent: boolean;              // 是否支持幂等重放
  execute(args: Record<string, unknown>): Promise<unknown>;
}
```

执行入口统一收口，这样"审批/幂等/超时/审计"只需要写一次：

```ts
export async function executeTool(name: string, args: Record<string, unknown>, ctx: { idempotencyKey?: string; approved: string[] }) {
  const tool = findTool(name);
  if (tool.level === 'L2' && !ctx.approved.includes(tool.name)) {
    return audit('blocked_permission', …), { approvalRequired: true };   // 转审批
  }
  if (tool.idempotent && ctx.idempotencyKey) { /* 命中直接回放 */ }
  return withTimeout(tool.timeoutMs, () => tool.execute(args));
}
```

> 关键纪律：**所有工具走同一个执行入口**。否则每加一个工具就要重新实现一遍安全逻辑，策略必然漂移。

## 4. 验证与观测

| 用例 | 期望 |
|---|---|
| 调 L0 工具 | 直接执行，审计 `success` |
| 调 L2 工具（未审批） | 返回审批请求，审计 `blocked_permission`，**不产生副作用** |
| 审批通过后重发 | 正常执行，且**只执行一次**（幂等） |
| 工具超时 | 返回结构化超时结果，Agent 循环继续 |
| 审计查询 | 能看到每条调用的工具名、结果、耗时、被拦原因 |

验收标准：

- [ ] 每个工具都标注了 level / timeout / idempotent
- [ ] L2 工具未审批时**绝对不执行**
- [ ] 审计里能区分四种 outcome
- [ ] 审计不会无限增长（有上限与截断）

## 5. 面试追问

> **Q：工具为什么必须分级？**
> 不分级只有两个结果：全都拦（体验不能用）或全放行（出事故）。分级让"只读"畅行、"不可逆"才打扰人。

> **Q：幂等键怎么做？**
> 客户端/编排层生成一个稳定 key（如 `业务ID + 工具名 + 参数摘要`），服务端缓存首次结果，同 key 重放。注意非终态（等待审批）**不能写缓存**，否则审批后重发会被挡住。

> **Q：工具超时应该抛异常还是返回结果？**
> 返回**结构化的超时结果**。抛异常会让上层分不清"工具报错"和"工具慢"，而这两者的处理策略完全不同（重试 vs 换工具）。

> **Q：为什么所有工具要共用一个执行入口？**
> 审批、幂等、超时、审计是横切关注点。分散实现必然出现"某个工具忘了做幂等"这类漏洞。

> **Q：审计为什么要有 outcome 而不是只记成功失败？**
> 因为"被拦下"才是最需要关注的事件——它说明有人（或模型）试图越界。没有 outcome 就发现不了攻击与误用。
