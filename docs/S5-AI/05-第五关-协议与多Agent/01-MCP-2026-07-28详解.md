# 01 · MCP 2026-07-28 详解

> **一句话**：MCP 解决的是"工具只在我自己应用里能用"——2026-07-28 之后它变得**无状态、可发现、可路由**，这才是它能进网关的前提。
>
> **前置**：[关卡概览](./index.md)
> **产出**：能徒手写出 `server/discover` / `tools/call` 的请求响应，并说清无状态化的收益
> **代码**：`apps/ai-course/server/mcp.ts`（教学版单端点）；后端参考 `backend/internal/mcp/`

---

## 1. 原理（够用即可）

MCP 是 Agent 与外部能力之间的**标准接口**。它把三件事标准化：

| 概念 | 含义 | 类比 |
|---|---|---|
| **Tools** | 可调用的函数（带 JSON Schema 参数） | 后端 API |
| **Resources** | 可读的数据（文档、数据库记录） | 静态资源 |
| **Prompts** | 服务端预置的提示模板 | 模板 |

传输是标准 **JSON-RPC 2.0** 信封：

```jsonc
// 请求
{ "jsonrpc": "2.0", "id": 1, "method": "tools/call", "params": { "name": "agent::search", "arguments": { "q": "报销" } } }
// 响应
{ "jsonrpc": "2.0", "id": 1, "result": { ... } }
```

## 2. 2026-07-28 的关键变化

### ① 无状态化：砍掉握手与会话

| 之前 | 2026-07-28 |
|---|---|
| 先 `initialize` 握手 | **没有握手**，第一个请求就是业务请求 |
| 服务端返回 `Mcp-Session-Id`，后续请求带上 | **没有会话 ID**，每个请求自包含 |
| 长任务靠会话维持 | 靠业务句柄 `taskId`（本仓库 TTL 10 分钟、`pollAfter` 1 秒） |

**收益（这是要在面试里讲出来的）**：任意实例都能处理任意请求 → 远程 MCP 可**无脑横向扩容**；故障切换不需要会话亲和；网关可以按请求内容做路由与限流。

代价：跨调用的上下文（如"上一步的结果"）必须由**业务自己**用句柄表达，协议不再替你保存。

### ② `server/discover` 与路由头

新增自描述方法 `server/discover`：返回协议版本、`serverInfo`、`capabilities`，客户端据此决定能用什么。

请求头三个（客户端每次都要带）：

| 头 | 作用 |
|---|---|
| `MCP-Protocol-Version` | 声明客户端使用的规范版本 |
| `Mcp-Method` | 方法名，供网关路由 |
| `Mcp-Name` | 目标工具/服务名，供网关限流 |

> 本仓库前端 `apps/ai-demo/src/services/aiApi.ts:207` 的裸请求**没有带这三个头**——这是个真实存在的欠账，可作为"工程细节决定能不能进网关"的例子。

### ③ MRTR：服务端反向索取输入

有时候工具执行到一半发现缺参数（比如缺审批人）。MRTR 的做法是：

1. 服务端返回 `resultType: "input_required"` + `inputRequests: [{id, type, prompt, required}]` + `requestState`
2. 客户端补齐后**重发原请求**，带上 `inputResponses` 与 `requestState`
3. 服务端从 context 里取 `inputResponses` 继续执行

注意：**它不是"再调一次新接口"，而是重发同一个请求**，所以幂等键必须一致。

### ④ 幂等：靠 `params._meta.idempotencyKey`

命中内存缓存直接回放结果（本仓库 TTL 10 分钟）。
关键规则：`input_required` 是**非终态，不写缓存**——否则客户端补齐后重发会被上次的"缺参数"结果挡住。

### ⑤ 双版本兼容

| 情况 | 行为 |
|---|---|
| 头缺失 | 按当前版本 `2026-07-28` 处理 |
| 旧版本（`2025-11-25` / `2025-06-18` / `2025-03-26`） | 正常处理，响应里注入 `warning` 并回写版本头 |
| 未知版本 | 返回 `-32600` |

兼容是渐进迁移的刚需：生态里不可能所有客户端同一天升级。

## 3. 代码实现（教学版）

`apps/ai-course/server/mcp.ts` 实现了一个**无状态单端点**，保留了协议的关键语义：

```ts
const PROTOCOL_VERSION = '2026-07-28';
const COMPATIBLE_VERSIONS = ['2025-11-25', '2025-06-18', '2025-03-26'];

// POST /api/mcp —— 无 initialize、无 session id，每个请求自包含
// 方法：server/discover / tools/list / tools/call / ping
export function handleMcp(request: { method: string; params?: unknown; id?: number|string|null },
                          headers: { protocolVersion?: string }) { ... }
```

响应里刻意带上 `warning`（旧版本时）与 `idempotent`（命中缓存时），让协议行为在 UI 上可见。

后端生产实现可直接对照：`backend/internal/mcp/{server.go,protocol.go,idempotency.go}`。

## 4. 验证与观测

```bash
# 自描述
curl -s -X POST http://localhost:5199/api/mcp \
  -H 'content-type: application/json' -H 'MCP-Protocol-Version: 2026-07-28' \
  -d '{"jsonrpc":"2.0","id":1,"method":"server/discover"}'

# 调工具（带幂等键）
curl -s -X POST http://localhost:5199/api/mcp \
  -H 'content-type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"knowledge.search","arguments":{"query":"报销"},"_meta":{"idempotencyKey":"k1"}}}'

# 旧版本协商
curl -s -X POST http://localhost:5199/api/mcp -H 'MCP-Protocol-Version: 2025-11-25' -d '...'
```

验收标准：

- [ ] 重复同一个 `idempotencyKey` 拿到同一个结果（幂等生效）
- [ ] 旧版本请求能成功且响应里带 `warning`
- [ ] 未知版本号返回 `-32600`
- [ ] 请求里**不出现**任何 session id

## 5. 面试追问

> **Q：MCP 和 Function Calling 是什么关系？**
> Function Calling 是**模型侧能力**（模型输出结构化调用意图）；MCP 是**工具侧协议**（工具怎么被发现、怎么被调用）。一个在你的应用里，一个跨应用。

> **Q：2026-07-28 为什么要去掉会话？**
> 会话让服务端有状态，就必须做会话亲和、扩容受限、故障切换复杂。去掉后每个请求自包含，任意实例可处理，网关也能按 `Mcp-Method`/`Mcp-Name` 路由限流。

> **Q：无状态后长任务怎么做？**
> 用业务句柄 `taskId`（本仓库 TTL 10 分钟）轮询 `tasks/get`，协议不再维护会话。

> **Q：MRTR 和"工具返回缺参数错误"有什么区别？**
> MRTR 是协议级约定：服务端给出结构化的 `inputRequests` + `requestState`，客户端**重发原请求**补齐，且幂等键保持一致；普通报错只是失败信息，客户端得自己猜怎么补。

> **Q：为什么 `input_required` 不能写幂等缓存？**
> 它是非终态。写进去的话客户端补齐后重发会被缓存里的"缺参数"结果挡住，永远走不下去。
