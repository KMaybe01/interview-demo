# 02 · 分块与 Embedding 策略

> **一句话**：RAG 的准确率上限，在建索引那一刻就定了——分块决定"能不能被检索到"，Embedding 决定"能不能被匹配上"。
>
> **前置**：[01-RAG全链路](./01-RAG全链路.md)
> **产出**：一套可替换的分块策略 + 一个可观测的检索质量基线
> **代码**：`apps/ai-course/server/rag.ts`、`apps/ai-course/src/stages/02-rag/RagStage.tsx`

---

## 1. 原理（够用即可）

RAG 是**离线建索引 + 在线检索**两段式：

```
离线：文档 → 解析 → 分块 Chunking → Embedding → 写入向量库
在线：问题 → Embedding → 召回 Top-K → 拼上下文 → LLM 生成
```

分块的本质矛盾：**块太大 → 噪声多、命中不精确；块太小 → 语义不完整、答案被切断**。

Embedding 的本质：把文本映射成向量，让"语义相近"变成"距离相近"。它解决的是**同义不同词**的问题（用户说"报销流程"，文档写"费用核销"）。

---

## 2. 企业实现要点

### 分块策略对比

| 策略 | 做法 | 优点 | 代价 |
|---|---|---|---|
| 固定长度 | 按字符数切，块间重叠 10-20% | 实现最简单、可预测 | 切断句子与表格 |
| **按结构** | 按 Markdown/HTML 标题层级切 | 保留语义单元，中文文档首选 | 需要解析标题树 |
| 语义切分 | 相邻句 Embedding 相似度骤降处断开 | 语义最完整 | 多一轮模型调用，成本高 |
| 小-大块 | 小块用于检索，命中后回填父块 | 精度 + 上下文兼得 | 索引结构复杂 |

**中文场景的实用起点**：按标题层级切到二级/三级标题，块大小 300-800 字，块间重叠 15%。再根据你的文档类型调。

### Embedding 选型的真实约束

| 约束 | 说明 |
|---|---|
| **换模型必须重建索引** | 不同模型的向量空间不可比。这是运维动作，不是改一行配置 |
| 语种覆盖 | 中文语料不足的模型，中文召回会明显变差 |
| 维度与成本 | 维度越高越准，但存储与检索开销越大 |
| 输入长度上限 | 超长块会被截断，等于丢信息 |

> 本仓库 Go 侧的 `OfflineProvider.Embed` 用的是「256 维哈希向量 + L2 归一化」——**不是真语义向量**，只用于离线兜底检索保证链路不空转。把它当对照：真线上要换真实 Embedding 模型。

### 元数据比向量更重要

生产环境里，一半以上的"检索不准"其实靠**过滤**解决，而不是靠向量：

```json
{ "docId": "handbook", "dept": "finance", "updatedAt": "2026-08-01", "acl": ["finance"] }
```

权限（ACL）、时效、部门，都要在召回**前**过滤——先过滤再召回，比召回后过滤便宜得多，也不会把无权内容送进模型。

## 3. 代码实现

教程代码先用**关键词检索（BM25 思路）**把链路跑通，这样零依赖就能验证"分块 + 召回 + 拼上下文"整个流程：

```ts
// apps/ai-course/server/rag.ts
export function chunkDocument(text: string, size = 500, overlap = 60): string[] { /* 按段落合并到 size，块间保留 overlap */ }
export function search(query: string, topK = 3): Chunk[] { /* 词频打分 + 排序，返回带 score 的块 */ }
export function buildContext(chunks: Chunk[]): string { /* 渲染成 `[n] (score=…) 内容` 供模型引用 */ }
```

换成向量检索时，**只有 `search()` 需要替换**——分块、拼装、引用渲染都不用动。这个边界就是刻意留出来的。

前端把召回结果直接展示出来，方便肉眼判断检索质量：

```tsx
{chunks.map((chunk, i) => (
  <div key={i}>[{i + 1}] score={chunk.score} … </div>
))}
```

## 4. 验证与观测

| 验证点 | 方法 |
|---|---|
| 分块是否合理 | 打印全部 chunk，看有没有把表格/代码块拦腰截断 |
| 召回是否正确 | 构造 10 个问题，人工标注"应该命中第几块"，算命中率 |
| 上下文是否溢出 | 检查注入后总 token 是否超过预算（超过就降 Top-K） |
| 权限是否生效 | 用无权限账号提问，确认召回结果里不出现受限文档 |

> 别只用"看起来答得不错"判断 RAG 好坏——那是在评测模型，不是评测检索。下一章会给可量化的办法。

## 5. 面试追问

> **Q：分块大小怎么定？**
> 没有万能值。经验起点 300-800 字（中文），块间重叠 15%。判断标准是"单独看这一块，能不能回答一个问题"——能就够大，不能就再大点。

> **Q：为什么要重叠？**
> 防止答案正好横跨切分点。重叠是拿索引体积换召回完整性。

> **Q：换 Embedding 模型要做什么？**
> 全量重建索引，且要灰度验证召回质量没退化。这是很多团队第一次换模型时踩的坑：忘了重建，检索质量断崖下跌。

> **Q：Top-K 越大越好吗？**
> 不是。K 大了噪声多、上下文长、成本高，还可能稀释关键信息。常见 3-8，配合 Rerank。

> **Q：权限过滤应该在召回前还是召回后？**
> 召回前（pre-filter）。召回后再过滤既浪费算力，又有把无权内容短暂送进上下文的风险。
