## 一、框架选型

### Q1: LangChain vs AI SDK 怎么选？

> | 维度 | LangChain | AI SDK |
> |------|-----------|--------|
> | **语言** | Python/JS | TypeScript |
> | **定位** | 全能框架 | 轻量前端优先 |
> | **React 集成** | 弱 | 原生 Hooks |
> | **学习曲线** | 陡峭 | 平缓 |
> | **生态** | 更大 | 快速增长 |
> | **适合场景** | 复杂后端编排 | 前端主导的 Agent |
>
> **选择依据**：
> - 前端团队 + React → AI SDK
> - Python 后端 + 复杂编排 → LangChain
> - 简单场景 → 手搓（不需要框架）

### Q2: AI SDK 的核心优势？

> **五大优势**：
> 1. **React 集成**：`useChat` Hook 开箱即用
> 2. **流式支持**：`streamText()` 一行代码
> 3. **类型安全**：TypeScript 原生支持
> 4. **轻量级**：没有多余抽象层
> 5. **Vercel 生态**：与 Next.js 无缝集成
>
> **核心 API**：
> - `generateText()`：非流式生成
> - `streamText()`：流式生成
> - `generateObject()`：结构化输出
> - `tool()`：定义工具

### Q3: LangGraph 是什么？

> **一句话**：LangChain 团队开发的状态机框架，用于构建复杂 Agent 工作流。
>
> **核心概念**：
> - **节点（Node）**：执行单元
> - **边（Edge）**：节点间的连接
> - **状态（State）**：节点间共享的数据
>
> **与 LangChain 的关系**：LangChain 是工具箱，LangGraph 是组装线。
>
> **适合场景**：多步骤 Agent、复杂工作流、需要状态管理的任务。

## 二、工程化实践

### Q4: 前端 AI 项目目录结构？

> **推荐结构**：
> ```
> src/
> ├── app/                    # Next.js App Router
> ├── components/
> │   └── ai/                # AI 相关组件
> │       ├── Chat.tsx       # 聊天界面
> │       ├── MessageList.tsx
> │       └── ToolResult.tsx
> ├── hooks/
> │   └── useChat.ts         # 聊天 Hook
> ├── lib/
> │   ├── ai.ts              # AI SDK 配置
> │   ├── tools.ts           # 工具定义
> │   └── prompts.ts         # Prompt 模板
> ├── api/
>   └── chat/route.ts        # API 路由
> ```

### Q5: AI API 路由怎么设计？

> **Next.js App Router 示例**：
> ```typescript
> // app/api/chat/route.ts
> import { streamText } from 'ai';
> import { openai } from '@ai-sdk/openai';
>
> export async function POST(req: Request) {
>   const { messages } = await req.json();
>
>   const result = streamText({
>     model: openai('gpt-4o'),
>     messages,
>     tools: { /* 工具定义 */ },
>   });
>
>   return result.toDataStreamResponse();
> }
> ```
>
> **关键点**：
> - 使用 `streamText()` 而非 `generateText()`
> - 返回 `toDataStreamResponse()` 格式
> - 前端用 `useChat()` 消费

### Q6: 如何处理工具调用结果？

> **AI SDK 处理流程**：
> ```typescript
> const result = await generateText({
>   model: openai('gpt-4o'),
>   messages,
>   tools: {
>     search: tool({
>       description: '搜索知识库',
>       parameters: z.object({ query: z.string() }),
>       execute: async ({ query }) => {
>         // 执行搜索
>         return searchResults;
>       },
>     }),
>   },
>   maxSteps: 10, // 允许多步工具调用
> });
> ```
>
> **关键点**：
> - `execute` 函数返回结果会自动传回 LLM
> - `maxSteps` 控制最大迭代次数
> - 工具调用失败会返回错误信息给 LLM

## 三、部署与运维

### Q7: AI 应用部署方案？

> **部署选项**：
> | 方案 | 适合场景 | 优点 | 缺点 |
> |------|---------|------|------|
> | **Vercel** | Next.js 应用 | 简单、自动扩展 | 冷启动 |
> | **Node.js 服务器** | 传统部署 | 灵活 | 需要运维 |
> | **Docker** | 容器化 | 一致性强 | 复杂度高 |
> | **Serverless** | 突发流量 | 按需付费 | 调试难 |
>
> **推荐**：中小项目用 Vercel，企业级用 Node.js + Docker。

### Q8: AI 应用可观测性怎么做？

> **三大支柱**：
> 1. **Trace**：完整调用链追踪
>    - 用户请求 → API → LLM → 工具 → 响应
>    - 工具：LangSmith、Helicone、自建
>
> 2. **Metrics**：关键指标监控
>    - 延迟、成功率、Token 消耗、成本
>    - 工具：Prometheus + Grafana
>
> 3. **Logging**：日志收集
>    - 输入输出、错误信息、调试日志
>    - 工具：ELK、Loki
>
> **优先级**：Metrics > Trace > Logging

### Q9: 如何控制 AI 成本？

> **六大策略**：
> 1. **模型选择**：简单任务用小模型
> 2. **Prompt 优化**：减少 Token 消耗
> 3. **缓存**：相同请求返回缓存
> 4. **限流**：控制 QPS 和并发
> 5. **批处理**：合并请求
> 6. **监控告警**：成本超阈值告警
>
> **经验**：80% 的成本可以通过 Prompt 优化和缓存降低。

## 四、性能优化

### Q10: 如何优化 AI 应用延迟？

> **优化方向**：
>
> **前端优化**：
> - 流式输出（用户感知延迟降低 50%）
> - 乐观更新（先显示，后验证）
> - 骨架屏（loading 状态）
>
> **后端优化**：
> - 并行工具调用
> - 预计算（Embedding 缓存）
> - 模型选择（小模型响应更快）
>
> **网络优化**：
> - CDN 加速
> - 连接复用
> - 数据压缩

### Q11: 如何优化 Token 消耗？

> **优化策略**：
> 1. **Prompt 精简**：删除冗余指令
> 2. **历史压缩**：摘要旧消息
> 3. **RAG 过滤**：只传相关段落
> 4. **结构化输出**：减少冗余格式
> 5. **模型选择**：简单任务用小模型
>
> **效果**：Prompt 优化可降低 30-50% Token 消耗。

## 五、面试速答

### Q12: 你用过哪些 AI 监控工具？

> | 工具 | 类型 | 特点 |
> |------|------|------|
> | **LangSmith** | SaaS | 功能最全 |
> | **Helicone** | SaaS | 成本分析好 |
> | **Phoenix** | 开源 | 可视化好 |
> | **自建** | 自建 | 完全可控 |
>
> **推荐**：初期用 Helicone（免费额度），生产用 LangSmith 或自建。

### Q13: AI 应用的测试怎么做？

> **测试策略**：
> 1. **单元测试**：工具函数测试
> 2. **集成测试**：API 路由测试
> 3. **端到端测试**：完整流程测试
> 4. **回归测试**：Prompt 变更后验证
>
> **挑战**：LLM 输出不确定，需要特殊断言。
>
> **方案**：LLM-as-Judge + 模糊匹配 + 人工抽检。
