### 25.1 最佳实践与反模式
### Q1: Go 项目中常见的“反模式”（Anti-patterns）有哪些？

**难度**：⭐⭐ | **频率**：📌 常考

**考点**：代码异味、过度设计、接口滥用、包循环依赖。

**💡 记忆关键词**：接口滥用、循环依赖、全局变量、错误忽略

**答案要点**：
- **接口滥用**：不要预先定义接口，应在需要解耦或测试时再定义（"Accept interfaces, return structs"）。
- **包循环依赖**：通过引入 `internal` 包或重构层级解决。
- **全局变量**：避免使用全局状态，改用依赖注入（DI）传递配置和客户端。
- **错误忽略**：禁止使用 `_` 忽略 `error`，必须显式处理或包装。

**📝 一句话总结**：反模式四宗罪，接口滥用循环依；全局变量错误忽，避免过度设计先。

### Q2: 如何设计一个可扩展的 Go 项目结构？

**难度**：⭐⭐ | **频率**：📌 常考

**考点**：Standard Go Project Layout、`cmd`/`internal`/`pkg` 分层。

**💡 记忆关键词**：cmd入口、internal私有、pkg公共、api契约

**答案要点**：
- **`cmd/`**：应用入口（如 `cmd/server/main.go`），仅包含初始化和启动逻辑。
- **`internal/`**：私有业务逻辑，禁止外部包导入（如 `internal/service`, `internal/handler`）。
- **`pkg/`**：可复用的公共库，可被外部项目引用（如 `pkg/logger`, `pkg/utils`）。
- **`api/`**：Protobuf 定义、OpenAPI 规范。
- **优势**：清晰的分层架构，便于测试、维护和团队协作。

**📝 一句话总结**：cmd入口internal私，pkg公共api契；分层架构清晰明，测试维护协作行。

### 25.2 配置与依赖管理
### Q3: 生产环境配置管理最佳实践？

**难度**：⭐⭐ | **频率**：📌 常考

**考点**：环境变量、配置中心、热更新、敏感信息保护。

**💡 记忆关键词**：12-Factor、viper配置、热更新、Vault加密

**答案要点**：
- **12-Factor App**：配置与代码分离，使用环境变量注入。
- **配置库**：使用 `viper` 支持多格式（YAML/JSON/ENV）和多来源（本地/远程）。
- **热更新**：监听文件变化或配置中心推送（如 etcd Watch），动态刷新配置无需重启。
- **安全**：敏感信息（DB 密码、API Key）存入 Vault 或 K8s Secrets，禁止硬编码。

**📝 一句话总结**：配置代码要分离，viper多源格式齐；热更新来免重启，Vault加密保安全。

### Q4: Go 项目如何分层？handler / service / repository 的边界怎么定？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：分层职责、依赖方向、接口放哪、常见错误分层。

**💡 记忆关键词**：依赖单向向内、handler 只做协议转换、service 编排业务、repo 只管数据、接口由使用方定义

**答案要点**：
- **三层职责**：

| 层 | 职责 | 不该做的事 |
|----|------|-----------|
| **handler / transport** | 解析请求、参数校验、调用 service、组装响应、HTTP 状态码 | 写业务规则、直接访问 DB |
| **service / usecase** | 业务编排、事务边界、跨领域协调、领域规则 | 依赖 `*gin.Context`、拼 SQL |
| **repository / dao** | 数据读写、SQL/ORM、缓存访问 | 写业务判断（如「余额不足」）、返回 HTTP 错误 |

- **依赖方向单向向内**：`handler → service → repository`，**内层不知道外层**（service 不应 import gin）。这是保证可测试性的关键：service 用接口注入 repo，单测直接 mock。
- **接口放在哪**：Go 的惯例是**接口由使用方（consumer）定义**，而不是实现方（实现方返回具体类型即可，调用方按需定义窄接口）。好处是避免「为每个 service 先写一遍大接口」的无意义抽象。
- **常见错误分层**：
  - handler 里直接调 GORM（换个协议/加个 MQ 消费者就没法复用）；
  - service 里 `c.JSON()`（依赖 HTTP 框架，无法被 gRPC/定时任务复用）；
  - repo 里抛业务错误（数据层不该知道「库存不足」这种业务语义）；
  - **共享 model 直接当 API 响应**（DB 字段变更直接破坏对外契约，还容易泄露敏感字段）。
- **事务边界**：事务放在 **service**（跨多个 repo 的操作），repo 只暴露「事务内可用」的句柄，避免在 repo 里嵌套事务。
- **目录参考（可落地）**：
  ```
  cmd/server/main.go        # 组装依赖、启动
  internal/handler/         # HTTP/gRPC 入口、DTO
  internal/service/         # 业务逻辑、事务
  internal/repository/      # 数据访问、SQL
  internal/domain/          # 领域模型与接口定义
  pkg/                      # 可被外部复用的库（谨慎）
  ```

**🔁 前端类比**：`components（展示）→ hooks（逻辑）→ api（数据）` 的分层是同构的；把业务写进组件、把请求写进组件，就是前端版的「错误分层」。

**📝 一句话总结**：handler 管协议、service 管业务与事务、repo 管数据，依赖单向向内；接口由使用方定义，事务边界在 service。

### Q5: 错误处理规范有哪些？常见反模式是什么？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：错误包装、错误判定、日志边界、哨兵错误。

**💡 记忆关键词**：%w 包装、errors.Is/As、只在边界记一次日志、不吞错、不滥用 panic

**答案要点**：
- **核心规范**：
  1. **错误必须被处理或向上返回**，绝不允许 `_ = err` 静默丢弃；
  2. **包装而非替换**：`fmt.Errorf("fetch user %d: %w", id, err)` —— `%w` 保留错误链，便于 `errors.Is/As` 判定；**注意不要泄漏敏感信息**（SQL、内部地址）；
  3. **只在「错误处理边界」记日志**（一般是 handler 或顶层），中间层只包装返回 —— 否则一个错误被打 5 遍日志，浪费且干扰排查；
  4. **判定用语义而非字符串**：`errors.Is(err, sql.ErrNoRows)`、`errors.As(err, &target)`（Go 1.26+ 有泛型的 `errors.AsType[T](err)`），**不要 `strings.Contains(err.Error(), ...)`**；
  5. **区分「预期内错误」与「异常」**：业务失败（余额不足）用 error + 明确错误码；`panic` 只用于「不可恢复的程序错误」（如初始化配置缺失），在顶层 `recover` 并转 500；
  6. **对外错误码统一**：定义错误码 + 用户可读消息，内部保留原始错误（日志），避免直接把 DB 错误抛给客户端。
- **常见反模式**：
  - 只 log 不返回（调用方继续往下跑，产生脏数据）；
  - 包装时丢掉原因（`errors.New("failed")`，失去链路）；
  - 同一错误多层重复日志；
  - 用 `panic` 做流程控制 / 在 goroutine 中 panic（**子 goroutine 的 panic 无法被父 goroutine recover**，需各自兜底，见 1-02 Q7）；
  - 自定义 error 类型但没有 `Unwrap()`，导致 `errors.Is/As` 失效。

```go
var ErrInsufficient = errors.New("insufficient balance") // 哨兵错误

func (s *Service) Transfer(ctx context.Context, from, to int64, amount int64) error {
    if err := s.repo.Deduct(ctx, from, amount); err != nil {
        if errors.Is(err, sql.ErrNoRows) {
            return fmt.Errorf("deduct from %d: %w", from, ErrInsufficient) // 语义清晰 + 保留链
        }
        return fmt.Errorf("deduct from %d: %w", from, err)
    }
    return nil
}

// handler 层统一记一次日志并映射状态码
if err := svc.Transfer(ctx, a, b, amt); err != nil {
    switch {
    case errors.Is(err, ErrInsufficient):
        return respond(w, http.StatusConflict, "BALANCE_NOT_ENOUGH")
    default:
        slog.Error("transfer failed", "err", err) // 只在这里记
        return respond(w, http.StatusInternalServerError, "INTERNAL")
    }
}
```

**📝 一句话总结**：`%w` 包装、`Is/As` 判定、只在边界记一次日志、对外统一错误码；不要吞错、不要重复日志、不要用 panic 做流程。

### Q6: Code Review 应该关注什么？如何写出好 review 的 PR？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：Review 优先级、PR 粒度、自动化前置、评审文化。

**💡 记忆关键词**：先正确性后风格、小 PR（<400 行）、可自动化的交给 CI、解释「为什么」

**答案要点**：
- **Review 关注顺序（重要 → 不重要）**：
  1. **正确性**：边界条件、错误处理、并发安全（共享状态/锁/goroutine 泄漏）；
  2. **接口与契约**：对外 API 是否兼容、命名是否清晰、可否演进；
  3. **可测试性与可观测性**：是否有测试、关键路径是否有日志/指标；
  4. **性能与资源**：是否有 N+1 查询、无界 channel/切片、未释放资源、锁里做 IO；
  5. **可读性与风格**：**风格交给 gofmt/golangci-lint 自动管**，人工只讨论有分歧的约定。
- **写一个好 PR**：
  - **小**（经验值 <400 行 diff）：大改动拆成「可独立合并的多步」（如先加字段、再写逻辑、最后切流量）；
  - **描述讲清 Why**：背景、方案、风险、回滚方式、验证方式（截图/压测/测试结果），而不是只贴 diff；
  - **自查先行**：作者自己先跑 lint/test，避免 reviewer 当人肉编译器；
  - **一次只做一件事**：把重构和新功能混在一起是最难 review 的做法；
  - **关联上下文**：关联 issue/需求、影响面（是否需 DB 变更、是否需要兼容旧客户端）。
- **评审文化**：
  - 评论区分**阻断（must fix）**与**建议（nit）**，别把 nit 当阻断；
  - 有疑问先问「这里是否考虑过 X」而不是「你错了」；
  - **自动化能管的绝不靠人**（格式化、lint、覆盖率、漏洞扫描都交给 CI，见 5-23 Q5）；
  - 明确 owner 与响应时限，避免 PR 堆积。

**📝 一句话总结**：Review 先看正确性与并发安全，再看契约与可观测性；PR 要小、讲清 Why、一次一件事，风格交给工具。

### Q7: 依赖管理与接口抽象的粒度怎么把握？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：go mod 依赖治理、接口粒度、DRY vs 过早抽象。

**💡 记忆关键词**：接口 1~3 个方法、使用方定义、不要为抽象而抽象、依赖最小化、定期升级

**答案要点**：
- **依赖治理**：
  - 用 `go mod tidy` 保持 `go.mod`/`go.sum` 干净；**禁止直接 `replace` 指向本地路径提交到主干**；
  - **依赖最小化**：每引入一个库都在增加长期维护与漏洞成本（**能用标准库就用标准库**，如 `log/slog` 取代 logrus、`net/http` 增强路由取代小框架）；
  - **定期升级**（月度）：`go list -m -u all` 看可升级项，配合 `govulncheck` 修漏洞；升级走小 PR + 回归测试，不要攒半年一次大升级；
  - 内部模块用 **monorepo/多模块** 拆分，避免「一个 util 包被全公司依赖」。
- **接口抽象的粒度**：
  - **Go 的惯例：接口小而专**（1~3 个方法，如 `io.Reader`、`io.Writer`），**由使用方定义**，实现方返回具体类型；
  - **只在真的需要时抽象**：① 需要 mock 以做单测；② 有多个实现；③ 需要打破循环依赖。**只有一个实现、且不需要 mock 时，先别写接口**；
  - 反模式：为每个 struct 配一个等价接口（纯噪音）、一个 30 方法的「大接口」（难实现难 mock，违反接口隔离）；
  - **重复优于错误的抽象**（"A little copying is better than a little dependency"）—— 过早抽象比适度重复代价更高。
- **判据一句话**：抽象的目的是**隔离变化点**。如果那个点不会变、也不会被替换/测试，抽象就是负债。

**📝 一句话总结**：依赖能用标准库就不用第三方并定期升级；接口由使用方定义、1~3 个方法、有真实需要（mock/多实现/解耦）才抽象。
