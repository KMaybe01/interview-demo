### 30.1 大厂真题精选
### Q1: 设计一个短链接生成系统（如 t.cn），要求高并发、低延迟。

**难度**：⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：Hash 算法、发号器、缓存策略、防冲突。

**💡 记忆关键词**：发号器、62 进制、Redis 缓存、302 跳转

**答案要点**：
- **发号方案**：使用 Redis `INCR` 或 Snowflake 算法生成唯一 ID，转为 62 进制短码。
- **存储**：MySQL 存映射关系，Redis 缓存热点短链（TTL 1 天）。
- **跳转**：301（永久，浏览器缓存）vs 302（临时，可统计点击）。推荐 302 便于数据分析。
- **防刷**：同一域名限制生成频率，恶意域名黑名单拦截。

### Q2: 如何实现一个分布式定时任务调度中心？

**难度**：⭐⭐⭐⭐ | **频率**：📌 常考

**考点**：时间轮、一致性 Hash、Leader 选举、失败重试。

**💡 记忆关键词**：时间轮调度、Leader 选举、一致性分配、指数退避

**答案要点**：
- **调度器**：使用 `cron` 表达式解析，基于时间轮（Time Wheel）或延迟队列触发。
- **执行器**：多节点部署，通过一致性 Hash 或轮询分配任务，避免重复执行。
- **高可用**：使用 etcd 或 Redis 实现 Leader 选举，主节点故障自动切换。
- **监控**：任务执行日志、成功率、耗时统计，失败自动重试（指数退避）。

### 30.2 场景设计题
### Q3: 设计一个支持千万级用户的在线状态查询系统。

**难度**：⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：Bitmap、Redis Set、WebSocket 推送、分库分表。

**💡 记忆关键词**：Bitmap 存储、WebSocket 推送、心跳机制、批量查询

**答案要点**：
- **状态存储**：Redis Bitmap 按天记录在线状态（`SETBIT uid 1`），空间极小（千万用户约 1.2MB/天）。
- **实时推送**：WebSocket 长连接维护用户会话，下线时更新状态并广播好友列表。
- **查询优化**：批量查询使用 `BITFIELD` 或 `MGET`；历史状态归档至 ClickHouse 或 ES。
- **一致性**：网络抖动导致状态不准，引入心跳机制（30s 无心跳判定离线）。

### Q4: 如何设计一个高可用的文件上传服务？支持断点续传、秒传。

**难度**：⭐⭐⭐⭐ | **频率**：📌 常考

**考点**：分片上传、MD5 校验、对象存储、CDN 加速。

**💡 记忆关键词**：MD5 秒传、分片上传、预签名 URL、CDN 加速

**答案要点**：
- **秒传**：计算文件 MD5，查询是否已存在，存在则直接返回 URL。
- **分片**：前端切片（如 5MB/片），并发上传，服务端合并分片。
- **存储**：直传 OSS/S3（预签名 URL），避免流量经过业务服务器。
- **高可用**：多可用区部署，CDN 边缘缓存热点文件，上传进度持久化至 Redis。

### Q5: 系统设计题的通用答题框架是什么？怎么做容量估算？

**难度**：⭐⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：需求澄清、容量估算、高层架构、深挖、量化表达。

**💡 记忆关键词**：四步法（澄清→估算→架构→深挖）、读写比、峰值系数 3~5、常用量级数字、主动说权衡

**答案要点**：
- **四步法（建议 45 分钟题的节奏）**：
  1. **澄清需求（5 min）**：功能范围（做什么/不做什么）、非功能指标（QPS、延迟、可用性、一致性）、规模量级（DAU、数据量、保留期）。**不澄清就画架构 = 直接扣分**。
  2. **容量估算（5 min）**：算 QPS、存储、带宽，推出实例数与存储选型。
  3. **高层架构（15 min）**：画数据流（客户端 → 网关 → 服务 → 存储/缓存/MQ），标出关键组件与选型理由。
  4. **深挖 2~3 点（15 min）**：选最有区分度的点展开（如「短链 ID 怎么生成」「如何保证不超卖」「如何做到低延迟」），并主动讲权衡。
- **估算常用数字（背下来，面试直接用）**：
  - 1 天 ≈ **86,400 秒 ≈ 10⁵ 秒**；1 万 QPS 意味着每天约 8.6 亿次请求；
  - 单机 Go 简单接口 ~**1~5 万 QPS**；Redis ~**10 万 QPS**；MySQL 单实例 ~**几千 QPS**（简单查询）；Kafka 单分区 ~**几 MB/s**；
  - **峰值系数**：日常 → 峰值通常 **3~5 倍**（大促 10 倍以上）；
  - 1 亿条 × 100 字节 ≈ **10 GB**；1000 万日活 × 每人 50 请求 ≈ **5 亿请求/天 ≈ 6000 QPS 均值**。
- **计算公式**：
  ```
  峰值 QPS = DAU × 人均日请求 ÷ 86400 × 峰值系数(3~5)
  存储 = 日增数据 × 保留天数 × 副本数 × 1.2
  实例数 = 峰值 QPS ÷ 单机 QPS ÷ 目标水位(0.6) × 冗余(1.5)
  ```
- **🔁 前端类比**：和「设计一个前端埋点 SDK / 虚拟列表」完全同构 —— 先问清量级（每天多少条埋点、列表多长），再决定方案（批量上报 / 虚拟滚动）。

**📝 一句话总结**：先澄清再画图，容量估算要给出数字与推导，架构分四层讲，最后深挖 2~3 个点并主动说权衡。

### Q6: 设计一个高并发秒杀系统（防超卖、防刷、防雪崩）。

**难度**：⭐⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：分层削峰、库存扣减一致性、限购与风控、降级。

**💡 记忆关键词**：层层拦截、Redis Lua 原子扣减、MQ 异步下单、DB 兜底 `WHERE stock > 0`、超时回补

**答案要点**：
- **核心矛盾**：瞬时流量极高（远超库存）、要求**不超卖**、要防机器刷单、不能拖垮整个系统。
- **分层削峰（从外到内每一层都拦掉 99%）**：
  1. **CDN / 静态化**：活动页静态资源全走 CDN，减少回源；
  2. **网关限流**：按用户/IP/商品维度限流（见 4-19 Q4），超出直接 429；
  3. **前端防重**：按钮置灰 + 一次性令牌（防重复提交，但**不可信**，只是第一道）；
  4. **Redis 预热库存**：活动前把库存加载到 Redis；
  5. **Redis 原子预扣**：Lua 脚本「判断库存 > 0 且用户未购买 → 扣减 → 记录用户」，保证原子性与幂等（防同一用户刷单）；
  6. **MQ 异步下单**：预扣成功即返回「排队中」，由消费者慢慢落库，实现流量削峰；
  7. **DB 最终扣减**：`UPDATE stock SET count = count - 1 WHERE sku_id = ? AND count > 0`（**靠 SQL 自身的原子性兜底，影响行数为 0 即失败**）。
- **防超卖的双保险**：Redis 预扣（性能）+ DB 条件更新/唯一约束（正确性）。**只靠 Redis 会有「缓存与 DB 不一致」风险，必须有对账/补偿**。
- **防刷**：答题/验证码、风控（设备指纹 + 行为）、**同用户限购**（Redis Set 记录已购）、黑名单。
- **防雪崩**：售罄后**直接降级**返回「已抢完」（不再打 DB）；秒杀服务**独立部署**与资源隔离；下游依赖全部设超时与熔断。
- **超时未支付回补**：用**延迟队列**（Redis ZSET / RabbitMQ 死信 / Kafka 时间轮）15 分钟未支付则回补库存。
- **异步结果查询**：客户端轮询「订单是否创建成功」，或走 WebSocket/SSE 推送（Go 很适合，见 6-29）。

**📝 一句话总结**：CDN/限流/前端 → Redis 原子预扣 + 用户去重 → MQ 异步下单 → DB 条件更新兜底；售罄即降级，超时未付自动回补。

### Q7: 设计一个支持百万连接的 IM 即时通讯系统。

**难度**：⭐⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：长连接接入、路由寻址、消息可靠投递、在线状态、扩散策略。

**💡 记忆关键词**：WebSocket/TCP、每连接 goroutine、uid→网关路由（Redis）、ack + 消息 ID 去重、写扩散 vs 读扩散

**答案要点**：
- **接入层**：`WebSocket`（或自定义 TCP 协议）。Go 的模型是**每连接 1~2 个 goroutine**（读循环 + 写循环）+ netpoller，百万连接的内存与调度开销完全可控（这是 Go 相对 Node/Java 的天然优势，可主动提）。
  - 关键配置：心跳（30~60s）与超时踢连接、读写缓冲、限流（单连接消息频率）、TCP `SO_REUSEPORT` + 多实例。
- **架构分层**：
  1. **接入网关（无状态）**：维护本机连接表 `uid → conn`，可水平扩展；
  2. **路由层**：`uid → 网关实例` 的映射存 Redis（或 etcd），跨机投递时先查路由再转发；
  3. **业务服务**：消息持久化、会话、群组、离线消息；
  4. **存储**：最近会话与未读用 Redis（ZSET/Hash），历史消息按 `会话ID + 时间` 分表落 MySQL/HBase，附件走对象存储。
- **消息可靠投递（三步）**：
  1. 发送方上行：客户端 → 服务端 `ack`（带服务端生成的 `msgID`）；
  2. 服务端下行：推送 `msgID` → 客户端 `ack` 回执；**未收到 ack 则在超时后重推**；
  3. **幂等去重**：客户端与服务端都用 `msgID` 去重（网络重试必然出现重复）。
- **顺序性**：同一会话的消息**串行处理**（按 `会话ID` 哈希到同一 goroutine/分区），保证会话内有序（全局有序成本过高，通常不要求）。
- **扩散策略（群聊 / Feed 同源问题）**：
  - **写扩散**：发送时写入每个接收者的收件箱（读快写慢，适合小群）；
  - **读扩散**：接收时拉取（写快读慢，适合大群）；
  - **推拉结合**：小群推、大群拉 + 在线推送。
- **在线状态**：`uid → 网关/时间戳` 存 Redis（分片或 bitmap），配合心跳刷新与过期；跨机房场景用 IM 自建状态服务，避免 Redis 成为单点。
- **离线消息**：用户上线时拉取未读（Redis 队列 + DB），超过 N 天的消息按需拉取历史。

**📝 一句话总结**：接入层无状态 + 路由表存 Redis + 消息 ack/去重保可靠 + 会话内串行保顺序 + 小群写扩散大群读扩散。

### Q8: 设计一个 Feed 流（关注时间线）系统。

**难度**：⭐⭐⭐⭐ | **频率**：📌 常考

**考点**：推拉模式、大 V 问题、分页方案、缓存与冷热分离。

**💡 记忆关键词**：写扩散（推）读快写慢、读扩散（拉）写快读慢、大 V 走拉、游标分页、Redis ZSET

**答案要点**：
- **需求特点**：读多写少、要求低延迟、关注关系不均匀（普通用户 vs 百万粉大 V）。
- **三种方案**：

| 方案 | 做法 | 优点 | 缺点 |
|------|------|------|------|
| **写扩散（推）** | 发帖时写入所有粉丝的收件箱 | 读极快（直接读自己收件箱） | 大 V 发一条要写百万次，写放大 |
| **读扩散（拉）** | 读时拉取所有关注人的最新帖并归并 | 写便宜 | 读慢，关注多时聚合成本高 |
| **推拉结合** | 普通用户推、大 V 拉 | 兼顾 | 实现复杂（本项目推荐答案） |
- **推拉结合细节**：活跃粉丝（近期登录）**推**到收件箱；大 V 与不活跃用户**拉**取；读取时「收件箱 + 拉取部分」归并排序。
- **存储**：
  - 收件箱：**Redis ZSET**（member = 帖子 ID，score = 时间戳/自定义排序权重），天然按时间倒序，`ZREVRANGEBYSCORE` 分页；
  - 冷数据：超过 N 天（如 7 天）的收件箱落 MySQL/HBase，读时回源合并；Redis 只保留热数据（可用 `ZREMRANGEBYRANK` 裁剪）。
- **分页**：**游标分页**（用上一页最后一条的 score/ID）而不是 offset —— offset 深分页既慢又会出现「重复/漏帖」。
- **一致性**：删帖 / 取关需要**异步清理**收件箱（MQ 消息驱动），允许短暂不一致（用户在意的优先级低）。
- **量级估算（顺带展示能力）**：1 亿日活、人均发 0.1 帖、平均 200 粉 → 写扩散 QPS ≈ 1e8 × 0.1 × 200 / 86400 ≈ **2.3 万 QPS**（这就是必须对大 V 走拉、且需要异步化的原因）。

**📝 一句话总结**：普通用户写扩散保读性能、大 V 读扩散避免写放大；收件箱用 Redis ZSET + 游标分页，冷数据下沉。

### Q9: 如何设计分布式 ID 生成服务？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：方案对比、Snowflake 细节、号段模式、可用性。

**💡 记忆关键词**：UUID 无序但简单、号段（Leaf）批量取号、Snowflake 趋势递增、时钟回拨、对外用过用 UUID

**答案要点**：

| 方案 | 有序性 | 性能 | 依赖 | 适用 |
|------|--------|------|------|------|
| UUID / ULID | UUID 无序；ULID 近似有序 | 极高（本地生成） | 无 | 对外 token、日志追踪 |
| DB 自增 | 有序 | 低（DB 瓶颈） | DB | 小规模、单库 |
| **号段模式（Leaf-segment）** | 有序 | 高（批量取号） | DB（可双 buffer 平滑） | 内部主键（推荐） |
| **Snowflake** | 趋势递增 | 极高（本地生成） | 依赖时钟与机器号分配 | 内部主键、高并发 |
| Redis INCR | 有序 | 高 | Redis（需持久化/高可用） | 中小规模 |

- **Snowflake 要点**：64 位 = 1 符号 + 41 时间 + 10 机器 + 12 序列（单机 4096 ID/ms）；**机器号分配**用 etcd/ZK/K8s StatefulSet 序号；**时钟回拨必须显式处理**（等待或拒绝，见 2-08 Q8）。
- **号段模式的妙处**：一次从 DB 取 1000 个号到内存，用完再取（DB 压力降到 1/1000）；用**双 buffer** 预取下一段，避免取号时的尖峰延迟。
- **高可用**：ID 服务本质是**无状态 + 依赖少数组件**，Snowflake 可本地嵌入业务进程（无网络调用）；号段模式需要 DB 高可用 + 兜底（DB 挂了用本地预留号段）。
- **安全注意**：**ID 泄露业务量**（自增 ID 能看出订单量）→ 对外展示用独立的 UUID/混淆 ID，内部主键保持有序。
- **热点问题**：Snowflake 生成的 ID 在同一毫秒内并发写会集中在相邻主键，可能造成**插入热点**（尤其分布式 DB）→ 可用号段模式打散或加随机后缀。

**📝 一句话总结**：内部主键用号段或 Snowflake（趋势递增、本地生成），对外标识用 UUID；机器号分配与时钟回拨是两个必须处理的细节。

### Q10: 系统设计如何主动暴露权衡与风险（面试加分项）？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：权衡表达、风险清单、演进路线、可运维性。

**💡 记忆关键词**：说代价、说瓶颈、说演进、对比「为什么不用另一个方案」、监控 + 灰度 + 回滚

**答案要点**：
- **主动说「代价」**：任何方案都有取舍，说完优点接着说成本。例：「用 Redis 预扣库存换性能，代价是多了一次最终一致性的对账逻辑」。
- **主动说「瓶颈在哪」**：指出当前设计的瓶颈与容量边界（如「收件箱写扩散在百万粉大 V 场景会放大 200 倍，所以我们让大 V 走拉取」）。
- **主动说「演进路线」**：给 v1 → v2 的路径，显示你不是只画理想架构。例：v1 单库 + 缓存 → v2 读写分离 + 分片 → v3 多机房。
- **主动做对比**：「我们没用 X 是因为……」——**对比即是深度**，也是面试官最常用的追问方式。
- **收尾必配三件事**：**监控指标**（QPS/P99/错误率/积压）、**灰度与回滚**（见 4-19 Q8）、**降级预案**（见 4-19 Q5）。这三点直接体现「能上生产」的思维。
- **反例（扣分行为）**：一上来就画一堆组件（Kafka、ES、Redis、分库分表全套）、不做估算、不说取舍、被追问就改口。

**📝 一句话总结**：好答案 = 方案 + 代价 + 瓶颈 + 演进 + 对比，最后补上监控/灰度/降级，让面试官看到「可运维、可回滚、能上生产」。
