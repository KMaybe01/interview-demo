### 22.1 认证与授权
### Q1: JWT 的工作原理是什么？如何安全地在 Go 中使用？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：Token 结构、签名算法、无状态认证、黑名单/刷新机制。

**💡 记忆关键词**：Header.Payload.Signature、短过期、Refresh Token、黑名单

**答案要点**：
- **结构**：Header.Payload.Signature，Base64 编码，不包含敏感信息。
- **签名**：使用 HS256（对称）或 RS256（非对称），Go 中推荐 `golang-jwt/jwt/v5`。
- **安全实践**：
  - 设置短过期时间（如 15 分钟），配合 Refresh Token 续期。
  - 敏感操作需二次验证。
  - 注销/踢人需引入 Redis 黑名单或版本号机制（JWT 本身无法主动失效）。

### Q2: 如何防止 CSRF 和 XSS 攻击？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：同源策略、Token 校验、内容安全策略。

**💡 记忆关键词**：SameSite、CSRF Token、输出转义、CSP

**答案要点**：
- **CSRF**：使用 `SameSite` Cookie 属性；表单提交携带自定义 Header 或 CSRF Token；验证 `Referer`/`Origin`。
- **XSS**：输出转义（Go `html/template` 默认转义）；设置 `Content-Security-Policy` (CSP) 头；避免 `innerHTML` 渲染不可信内容。

### 22.2 数据加密
### Q3: Go 中如何实现敏感数据加密存储（如密码、身份证号）？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：哈希加盐、对称/非对称加密、密钥管理。

**💡 记忆关键词**：bcrypt/argon2、AES-GCM、KMS、mTLS

**答案要点**：
- **密码**：使用 `bcrypt` 或 `argon2` 进行单向哈希，绝对禁止明文或 MD5/SHA1。
- **敏感字段**：使用 AES-GCM（对称加密）加密后存 DB，密钥通过 KMS（如 AWS KMS、HashiCorp Vault）管理，禁止硬编码。
- **传输**：全站 HTTPS，内部服务启用 mTLS。

### Q4: HTTPS/TLS 握手过程是怎样的？Go 如何配置 TLS 与 mTLS？

**难度**：⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：握手流程、TLS 1.3 变化、证书校验、Go 的 `tls.Config`。

**💡 记忆关键词**：ClientHello/ServerHello、CA 链校验、TLS1.3 只留 (EC)DHE、前向安全、mTLS 双向验证

**答案要点**：
- **TLS 1.2 握手（2-RTT 概要）**：`ClientHello`（随机数、支持的套件）→ `ServerHello` + **证书链** + 密钥交换参数 → 客户端**校验证书**并生成预主密钥 → 双方用随机数派生会话密钥 → `Finished` 验证握手完整性。
- **TLS 1.3（1-RTT，支持 0-RTT）**：**删除了 RSA 密钥交换与一堆老套件**，只保留 (EC)DHE 等具备**前向安全**的密钥交换；握手消息加密，套件精简。Go 1.22+ 默认最小版本已是 TLS 1.2，Go 1.27 起旧的 `tls10server`/`tls3des`/`tlsrsakex` 等 `GODEBUG` 兼容开关被移除。
- **证书校验要点**：**主机名匹配**、有效期、完整 CA 链、吊销状态；企业内网 + 双向认证场景用 **mTLS**（服务间互验身份，替代弱鉴权）。
- **Go 配置**：
  - 服务端：`http.Server{TLSConfig: &tls.Config{MinVersion: tls.VersionTLS12}}`；
  - 客户端：显式设置 `MinVersion`、`RootCAs`（自签场景），**不要**在生产用 `InsecureSkipVerify: true`；
  - **mTLS**：服务端 `ClientAuth: tls.RequireAndVerifyClientCert` + `ClientCAs`。
- **面试加分**：Go 1.24 起 `crypto/tls` **默认启用后量子混合密钥交换 `X25519MLKEM768`**；Go 1.27 新增 `crypto/mldsa`（FIPS 204 签名）与 TLS 中的 MLDSA 套件 —— 能说出「PQC 已进入标准库」是明显的新版本敏感度。

```go
srv := &http.Server{
    Addr: ":8443",
    TLSConfig: &tls.Config{
        MinVersion: tls.VersionTLS12,
        ClientAuth: tls.RequireAndVerifyClientCert, // mTLS
        ClientCAs:  clientCAPool,
    },
}
_ = srv.ListenAndServeTLS("server.crt", "server.key")
```

**📝 一句话总结**：HTTPS = 非对称协商密钥 + 对称加密传输 + 证书验身份；TLS 1.3 只留前向安全套件，Go 里显式设 `MinVersion`，内网服务间用 mTLS。

### Q5: 对称加密、非对称加密、哈希如何选型？AES-GCM 有什么坑？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：三类算法定位、混合加密、密码存储、GCM nonce 唯一性。

**💡 记忆关键词**：对称快（AES）、非对称慢（RSA/ECC）、哈希不可逆、密码必须 bcrypt/argon2 加盐、GCM nonce 绝不能重复

**答案要点**：

| 类型 | 代表 | 特点 | 典型用途 |
|------|------|------|----------|
| 对称 | AES-256、ChaCha20 | 快，**密钥必须保密** | 大数据量加解密、TLS 会话数据 |
| 非对称 | RSA、ECC(ECDSA/X25519) | 慢（约慢 2~3 个数量级），公私钥分离 | 密钥交换、数字签名、证书 |
| 哈希 | SHA-256、SHA-3 | **不可逆**、定长输出 | 完整性校验、签名摘要 |

- **实际系统用「混合加密」**：非对称协商/分发对称密钥，再用对称加密数据（TLS 就是这个模型）。
- **密码存储绝不能用哈希裸存**：必须用**慢哈希 + 每用户随机盐**（`golang.org/x/crypto/bcrypt`、`scrypt`、`argon2id`）；MD5/SHA-1/SHA-256 直存密码在面试中等于直接失分。
- **AES-GCM 的坑**：
  1. **同一密钥下 nonce 绝不能重复**（重复会泄漏密钥流、可伪造认证标签）—— 必须用计数器或随机 nonce 并保证唯一，随机 nonce 建议 ≥96 位；
  2. **不要自己拼「加密 + 签名」**，优先选 AEAD（GCM/ChaCha20-Poly1305）一次性提供机密性 + 完整性；
  3. 密钥必须来自 `crypto/rand`，不要用 `math/rand`、时间戳、用户输入派生；
  4. Go 1.24 起提供 `cipher.NewGCMWithRandomNonce`，**自动生成随机 nonce 并前置到密文**，能在 API 层面避免 nonce 复用。
- **服务端常见需求对应**：字段级加密（手机号/身份证）用 AES-GCM + KMS 托管密钥；传输用 TLS；签名验签用 ECDSA/Ed25519。

```go
block, _ := aes.NewCipher(key)                  // key 必须 16/24/32 字节，来自 crypto/rand
aead, _ := cipher.NewGCMWithRandomNonce(block)  // Go 1.24+：自动随机 nonce，防重复
ciphertext := aead.Seal(nil, nil, plaintext, nil)
plaintext2, _ := aead.Open(nil, nil, ciphertext, nil)
```

**📝 一句话总结**：数据用对称、密钥用非对称、完整性用 AEAD；密码用 bcrypt/argon2 加盐，AES-GCM 的 nonce 一次都不能重复。

### Q6: 如何防止 SQL 注入、SSRF 与越权访问？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：参数化查询、SSRF 白名单、水平/垂直越权、统一鉴权。

**💡 记忆关键词**：参数化查询（占位符）、ORM Raw 也是拼接、SSRF 防内网与元数据、越权必须服务端校验归属

**答案要点**：
- **SQL 注入**：
  - 唯一正解是**参数化查询**（预编译占位符）：`db.Query("SELECT * FROM users WHERE name = ?", name)`；
  - GORM 用 `Where("name = ?", name)` / `Where(&User{Name: name})`；**`Where(fmt.Sprintf(...))` 与 `.Raw()` 拼接同样会注入**；
  - 加固：DB 账号最小权限（禁 `DROP`/文件读写）、错误信息不回显 SQL、动态排序字段用**白名单映射**而非直接拼接列名。
- **SSRF（服务端请求伪造）**：
  - 场景：服务端根据用户传入的 URL 去抓取（图片代理、Webhook、URL 预览）；
  - 防护：**域名/IP 白名单**（最有效）、**禁止内网与元数据地址**（`127.0.0.0/8`、`10.0.0.0/8`、`169.254.169.254`、`::1`）、**禁用或校验重定向**（每跳都要校验）、限制协议为 http/https、独立出口与超时控制。
- **越权（最容易被忽视）**：
  - **水平越权**：改 `?userId=123` 拿别人数据 → **必须服务端校验资源归属**：`WHERE id = ? AND owner_id = currentUserID`，绝不信任前端传的 ID；
  - **垂直越权**：普通用户调用管理员接口 → 统一**鉴权中间件**按路由声明所需权限（RBAC），而不是靠前端隐藏按钮；
  - 兜底：统一在 repository 层强制拼接租户/用户过滤条件，避免「漏写一个条件就全表泄露」。
- **其他常见项**：CORS 白名单（不要 `*` + credentials）、上传类型与内容双重校验 + 不落可执行目录、登录接口限流与验证码防爆破、敏感操作二次验证。

**📝 一句话总结**：注入靠参数化，SSRF 靠白名单与内网封禁，越权靠「服务端强制校验资源归属 + 统一鉴权中间件」。

### Q7: OAuth2 / OIDC 与 RBAC 在 Go 服务中如何落地？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：授权模式选型、OIDC 与 JWT 关系、网关鉴权、RBAC 实现。

**💡 记忆关键词**：授权码 + PKCE、客户端凭证、OIDC = OAuth2 + id_token、网关校验、RBAC 位运算/Casbin

**答案要点**：
- **OAuth2 四种授权模式**：
  1. **授权码模式（Authorization Code + PKCE）**：最推荐，Web/SPA/移动端都适用；PKCE 防授权码拦截；
  2. **客户端凭证（Client Credentials）**：**服务间调用**（无用户参与）标配；
  3. **隐式模式（Implicit）**：因令牌暴露在 URL，**已废弃**，SPA 也应改用授权码 + PKCE；
  4. **密码模式**：仅遗留系统，新系统不要用。
- **OIDC = OAuth2 + 身份层**：多了 `id_token`（JWT，含 `sub`/`iss`/`aud`/`exp` 等）与 `/userinfo` 端点，用于**统一登录 SSO**；区分 **access_token（访问资源）** 与 **id_token（证明身份）** 是常见考点。
- **Go 服务落地**：
  1. **网关/中间件统一鉴权**：校验签名（JWKS 拉公钥 + 缓存）、校验 `iss`/`aud`/`exp`、解析 `scope`/`roles` 注入 context；**不要每个 handler 各写一遍**；
  2. **RBAC**：角色 → 权限集合的映射。小规模可用**位运算**（本仓库 `backend/internal/rbac` 就是位运算实现：`perm & required != 0`），复杂场景用 **Casbin**（支持 RBAC/ABAC 模型与策略文件）；
  3. **细粒度授权**：数据级权限放到 repository 层强制过滤（见 Q6），不要只做接口级。
- **Token 生命周期**：access_token 短（5~15 分钟）+ refresh_token 长且可撤销（存 Redis 白名单/黑名单），配合 token 轮换与重放检测（本仓库 `backend/internal/auth` 的 JWT 双 Token + Session Nonce 就是这套）。

**📝 一句话总结**：Web/移动端用授权码 + PKCE、服务间用客户端凭证；鉴权统一放网关/中间件，权限映射用位运算或 Casbin，数据级权限下推到 repository。

### Q8: 密钥如何管理？如何进行轮换与脱敏？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：密钥不落仓库、KMS 信封加密、轮换、日志脱敏。

**💡 记忆关键词**：环境变量/KMS/Vault、信封加密（DEK + KEK）、kid 版本轮换、日志脱敏、前端不留密钥

**答案要点**：
- **基本红线**：
  - 密钥**绝不进代码仓库与镜像**（`.env` 加入 `.gitignore`，只提交 `.env.example`）；一旦误提交要**立即轮换**（历史仍在 git 里）；
  - 配置来源优先级：**KMS/密钥服务（Vault、云 KMS/Secrets Manager）> 环境变量 > 配置文件**；配置文件最弱。
- **信封加密（Envelope Encryption）**：数据用**数据密钥 DEK** 加密，DEK 用**主密钥 KEK**（KMS 托管、不出 KMS）加密后随数据存库；解密时用 KMS 解开 DEK。好处：KMS 只承担少量密钥运算，海量数据加密不受性能限制。
- **轮换策略**：
  - 给密钥加**版本号 `kid`**，支持多密钥并存：**新数据用新密钥，旧数据渐进重加密**（可后台异步迁移）；
  - JWT 用 `kid` 支持签名密钥轮换（JWKS 里一次性发布多个公钥）；
  - 定期轮换 + 怀疑泄露时**立即轮换**，并保留旧密钥一段兼容期。
- **脱敏与最小暴露**：
  - 日志**禁止打印** token、密码、身份证、银行卡、密钥；统一在日志中间件做脱敏（正则/字段掩码）；
  - 接口返回**最小字段集**（DTO 显式声明，不要直接序列化 DB model 带上敏感字段）；
  - 错误响应不要回显内部异常与堆栈（可能含连接串、路径）。
- **🔁 前端提醒（面试常被追问）**：前端的 `VITE_*` 环境变量**会被打进产物、是明文**，因此**任何密钥都不能放前端**；前端能做的只有「不落敏感数据到 localStorage、不把 token 放 URL」。

**📝 一句话总结**：密钥进 KMS/Vault 不进仓库，用信封加密减少 KMS 压力，靠 `kid` 做多版本轮换，日志与响应双向脱敏。
