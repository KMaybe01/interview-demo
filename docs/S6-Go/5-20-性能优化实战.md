### Q1: 线上服务频繁 Full GC 如何排查与优化？

**难度**：⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：GC 触发阈值、内存分配模式、对象生命周期、`GOGC` 调整。

**💡 记忆关键词**：gctrace 追踪、pprof 分析、sync.Pool 复用、GOGC 调参

**答案要点**：
- **排查**：使用 `go tool pprof -alloc_space` 查看内存分配热点；开启 `GODEBUG=gctrace=1` 观察 GC 频率与暂停时间。
- **优化策略**：
  1. 减少短期对象分配（复用 buffer、`sync.Pool`）。
  2. 避免大对象频繁创建（如大切片、大 Map）。
  3. 调整 `GOGC` 参数（默认 100，可适当调高至 200~500 降低 GC 频率，但会增加内存占用）。
  4. 使用 `debug.FreeOSMemory()` 主动释放内存（谨慎使用，可能引发 STW）。

### Q2: 如何优化高并发下的 JSON 序列化性能？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：反射开销、预编译、`jsoniter`/`sonic`、结构体标签。

**💡 记忆关键词**：反射开销、sonic/jit、easyjson 生成、omitempty 精简

**答案要点**：
- 标准库 `encoding/json` 使用反射，性能较低。
- **优化方案**：
  1. 使用 `json-iterator/go` 或字节跳动开源的 `sonic`（基于 JIT 编译，性能提升 3~10 倍）。
  2. 结构体字段使用 `json:"name,omitempty"` 减少冗余。
  3. 对热点路径手动序列化或使用代码生成工具（如 `easyjson`）。
  4. 避免在循环中重复 `json.Marshal`，预编译 Schema 或使用池化 Encoder。

### Q3: 如何优化 Go 服务的 TCP 连接数与文件描述符限制？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：`ulimit`、连接池、TIME_WAIT 处理、内核参数调优。

**💡 记忆关键词**：ulimit 调高、连接池复用、Keep-Alive、TIME_WAIT 优化

**答案要点**：
- 系统层：调整 `ulimit -n`（默认 1024，生产建议 65535+）；优化 `net.ipv4.tcp_tw_reuse`、`tcp_fin_timeout`。
- 应用层：
  1. 使用连接池复用 HTTP/gRPC 连接（`http.Transport.MaxIdleConns`）。
  2. 避免频繁短连接，启用 Keep-Alive。
  3. 监控 `netstat` 状态，排查 `CLOSE_WAIT` 泄漏（代码未正确 Close）。

### Q4: 如何用 pprof 定位 CPU 热点？（完整方法论）

**难度**：⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：pprof 接入、采样方式、火焰图判读、flat vs cum。

**💡 记忆关键词**：net/http/pprof 挂载、profile?seconds=30、top/list/web、flat 自身 vs cum 调用链、先测量再优化

**答案要点**：
- **接入**：
  - HTTP 服务：`import _ "net/http/pprof"` 后访问 `/debug/pprof/`（**生产环境务必放独立端口或加鉴权**，否则等于开了个性能分析后门）；
  - 非 HTTP 程序：`runtime/pprof` 手动 `StartCPUProfile`。
- **采集**：`go tool pprof -http=:8081 http://host:6060/debug/pprof/profile?seconds=30`
- **判读顺序**：
  1. 看 **`top -cum`**：谁是耗时最大的调用链（包含子调用），先找「大头」；
  2. 再看 **`top`（flat）**：**自身**耗时最大的函数 —— 这才是要改的代码；
  3. 打开**火焰图**：横向宽度 = 采样占比，找最宽的「平顶」函数；
  4. `list FuncName` 看具体到行的耗时。
- **区分系统开销**：`runtime.gcBgMarkWorker`、`runtime.mallocgc`、`runtime.schedule` 占比高说明问题在**分配/GC/调度**，而不是业务逻辑（对应优化手段见 2-06、Q5/Q6）。
- **常见结论与对策**：反射/`encoding/json` 热 → 换 `sonic`/`easyjson` 或减少序列化；字符串 `+` 拼接热 → `strings.Builder`；`map` 操作热 → 预分配容量、换分片；锁 `sync.Mutex` 热 → 缩小临界区、分片。
- **PPROF 采样本身有开销**（CPU profile 默认 100Hz，通常 <5%），但应在**压测环境**或单实例灰度时采。

**📝 一句话总结**：`top -cum` 找大头、`top` 找自身热点、火焰图看宽度、`list` 定位到行；先测量再动手。

### Q5: 内存持续上涨怎么排查？如何区分泄漏与缓存？

**难度**：⭐⭐⭐⭐ | **频率**：🔥 高频

**考点**：heap profile、inuse vs alloc、diff 对比、常见泄漏源、GOMEMLIMIT。

**💡 记忆关键词**：inuse_space vs alloc_space、-base 做 diff、全局 map 只增不减、goroutine 泄漏、GOMEMLIMIT 软限制

**答案要点**：
- **先分类**：① **真泄漏**（对象被引用，GC 收不掉）；② **缓存/池**（有上限，属正常增长后趋稳）；③ **分配速率高**（GC 追不上，表现为 GC CPU 高与 RSS 上涨）。
- **采集**：`/debug/pprof/heap`，关注 **`inuse_space`**（当前存活对象，判断泄漏）与 **`alloc_space`**（累计分配，判断分配热点）。
- **对比法最有效**：采两个时间点的 profile 做 diff `-base`，增长的部分就是嫌疑：
  ```bash
  go tool pprof -base heap1.pb.gz heap2.pb.gz   # 只看「新增」的内存
  ```
- **常见泄漏源（可按此清单逐条排查）**：
  1. **全局 map / slice 只增不减**（缓存无淘汰、注册表未注销）；
  2. **goroutine 泄漏**（连带其栈与引用对象一起泄漏，见 1-03 Q12）；
  3. **`time.Ticker` / `time.Timer` 未 `Stop`**，`context` 未 `cancel`；
  4. **slice 截取保留大数组**：`s := big[0:2]` 会让 4MB 底层数组无法回收 → 用 `slices.Clone` 或 `copy` 到新切片；
  5. **闭包/回调持有大对象**（如把整个 request 对象挂在长生命周期结构里）；
  6. **`sync.Pool` 误用**：把 Pool 当长期缓存，对象被 GC 回收后又重新分配（不泄漏，但吞吐抖动）。
- **辅助手段**：`GODEBUG=gctrace=1` 看 GC 频率与堆大小；`runtime/metrics` 的 `/memory/classes/heap/objects:bytes`；`GOMEMLIMIT`（Go 1.19+）设置**软内存上限**，让 GC 在接近上限时更激进，避免被 OOM Killer 杀掉（比单纯调 `GOGC` 更稳）。

**📝 一句话总结**：用 `inuse_space` 判断泄漏、`-base` diff 找增长点，依次排查「全局容器、goroutine、Ticker/context、slice 截取」，最后用 `GOMEMLIMIT` 兜底。

### Q6: 锁竞争严重导致延迟抖动，怎么优化？

**难度**：⭐⭐⭐⭐ | **频率**：📌 常考

**考点**：mutex/block profile、缩小临界区、分片、原子、串行化。

**💡 记忆关键词**：SetMutexProfileFraction、锁外做 IO、分片锁、原子替代、减少共享

**答案要点**：
- **确认是锁问题**：开启采样 `runtime.SetMutexProfileFraction(1)`（及 block profile `SetBlockProfileRate`），采集 `/debug/pprof/mutex`、`/debug/pprof/block` —— **mutex profile 统计的是「等锁时长」**，能直接指出争抢最严重的锁。
- **典型症状**：P99 抖动、CPU 大量消耗在 `futex`/`runtime.lock2`、吞吐随并发上升反而下降。
- **优化手段（按收益排序）**：
  1. **缩小临界区**：把 IO、序列化、日志、计算移到锁外；只保护真正的共享读写；
  2. **减少共享**：每个 goroutine 用自己的局部变量，最后合并（见 1-03 Q10 的 `results[i]` 写法）；
  3. **分片（sharding）**：大 map 拆成 N 个分片各带锁，竞争降到 1/N（见 2-08 Q7）；
  4. **原子操作替代锁**：单变量计数/标志用 `atomic.Int64`（见 1-03 Q14）；
  5. **读写分离**：读多写少用 `RWMutex`（注意写者可能饥饿，且会拖慢读）；
  6. **串行化 + channel**：把共享状态收敛到**单个 goroutine** 里（actor 模式），外部用 channel 交互 —— 无锁但要注意队列延迟；
  7. **`sync.Pool`**：减少高频分配带来的 GC 与分配器内部锁竞争。
- **别忘了排查前提**：容器环境先确认不是「GOMAXPROCS 与 CPU limit 不匹配」造成的抖动（Go 1.25+ 已自动容器感知，见 2-05 Q2）。

**📝 一句话总结**：先用 mutex profile 定位争抢最狠的锁，再依次「缩小临界区 → 减少共享 → 分片 → 原子 → 串行化」。

### Q7: Benchmark 怎么写才准确？`B.Loop` 解决了什么问题？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：基准测试规范、防止优化掉、`-benchmem`、benchstat、`B.Loop`。

**💡 记忆关键词**：b.ReportAllocs、结果要「用掉」、b.ResetTimer、benchstat 对比、B.Loop 只 setup 一次

**答案要点**：
- **三种常见错误**：
  1. **结果没被使用** → 编译器把整个循环优化掉，测出「0 ns/op」；
  2. 把**准备数据/建表**放进了计时区间 → 用 `b.ResetTimer()` 之前完成；
  3. 只跑一次、只看一次 → 噪声大，需 `-count=10` + **benchstat** 比较。
- **正确姿势**：
  ```go
  var sink []byte // 包级变量，防止结果被优化掉

  func BenchmarkMarshal(b *testing.B) {
      v := buildLargeStruct()      // setup：在计时之外
      b.ReportAllocs()
      b.ResetTimer()
      for b.Loop() {               // Go 1.24+：等价于 for i := 0; i < b.N; i++
          data, err := json.Marshal(v)
          if err != nil {
              b.Fatal(err)
          }
          sink = data
      }
  }
  ```
  ```bash
  go test -run '^$' -bench . -benchmem -count=10 ./... | tee new.txt
  benchstat old.txt new.txt      # 输出 Δ% 与显著性，避免「凭感觉快」
  ```
- **`B.Loop`（Go 1.24+）相对 `b.N` 的两点改进**：① 基准函数**每个 `-count` 只执行一次**，昂贵的 setup/cleanup 不会被重复执行；② 循环体内的**函数传参与返回值会被保持存活**，不会被编译器优化掉。Go 1.26 还修复了 `B.Loop` 阻止内联的问题。
- **⚠️ 微基准 ≠ 生产性能**：benchmark 只能验证局部假设（如「换 `strings.Builder` 减少 50% 分配」），真实收益要用 **pprof + 线上指标**验证。

**📝 一句话总结**：结果要用掉、setup 移出计时、`-benchmem -count=10` 配合 benchstat；`B.Loop` 让 setup 只跑一次且结果不被优化掉。

### Q8: 偶发毛刺（P99 抖动）如何用 trace / FlightRecorder 定位？

**难度**：⭐⭐⭐⭐ | **频率**：📌 常考

**考点**：trace 判读、毛刺常见原因、FlightRecorder 常驻采样。

**💡 记忆关键词**：go tool trace 看 P 利用率、GC/STW、syscall 阻塞、cgroup throttle、FlightRecorder 环形缓冲

**答案要点**：
- **什么时候用 trace 而不是 pprof**：pprof 给的是**统计分布**（谁占 CPU 多），trace 给的是**时间线**（某一刻发生了什么）。**偶发毛刺必须用 trace**。
- **采集**：
  - HTTP：`/debug/pprof/trace?seconds=5`；
  - 代码内：`runtime/trace.NewFile` + `trace.Start/Stop`；
  - 打开：`go tool trace trace.out`（新版 UI 看 P 时间线、GC、网络阻塞、Syscall、STW）。
- **trace 里重点看**：
  1. **P 是否有空闲/长时间被占用**（说明并发度或阻塞问题）；
  2. **GC 的 STW 与 mark assist**（分配太快会把业务线程拉去帮 GC）；
  3. **Syscall/网络阻塞**（DNS、日志同步写盘、慢下游）；
  4. **Goroutine 就绪延迟**（`/sched/latencies` 指标同源，说明调度排队）。
- **毛刺常见元凶清单**：GC（堆增长或 `GOGC` 过小）、锁竞争、**日志同步写盘/`fmt.Println` 大字符串**、DNS 解析（本地缓存缺失）、连接池耗尽后的排队、`netpoller` 唤醒延迟、**容器 CPU 被 cgroup 限流（throttle）**、定时任务与大请求撞在一起。
- **FlightRecorder（Go 1.25+）**：`runtime/trace.FlightRecorder` 常驻把 trace 写进**内存环形缓冲**，出问题时 `WriteTo` **只 dump 最近几秒**——body 极小、几乎无开销，正是为「偶发问题无法预测何时采集」设计的。

```go
fr := trace.NewFlightRecorder(trace.FlightRecorderConfig{MinAge: 5 * time.Second})
if err := fr.Start(); err != nil { log.Fatal(err) }
defer fr.Stop()

onSlowRequest := func() { // 例如 P99 超阈值时触发
    f, _ := os.Create("flight.trace")
    defer f.Close()
    _ = fr.WriteTo(f) // 只保存最近几秒
}
```

**📝 一句话总结**：毛刺用 trace 看时间线（P 利用率/GC/阻塞），无法复现就用 FlightRecorder 常驻环形缓冲、出事再 dump。

### Q9: 线上服务 CPU 飙高如何排查？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：`pprof` CPU profile、火焰图、热点函数定位。

**💡 记忆关键词**：pprof 抓包、火焰图、热点函数、死循环 GC

**答案要点**：
1. 开启 `pprof` 端点，抓取 CPU profile：`go tool pprof http://localhost:6060/debug/pprof/profile?seconds=30`。
2. 使用 `top` 命令查看耗时最高的函数。
3. 生成火焰图（Flame Graph）直观查看调用栈热点。
4. 结合代码分析：是否存在死循环、频繁 GC、正则回溯、锁竞争（Mutex Profile）或序列化瓶颈。
