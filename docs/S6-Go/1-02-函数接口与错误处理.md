### Q1: Go 的接口（Interface）是鸭子类型吗？如何实现多态？

**难度**：⭐⭐ | **频率**：🔥 高频

**考点**：隐式实现、接口表、动态派发。

**💡 记忆关键词**：鸭子类型、隐式实现、iface/eface、动态分发

**答案要点**：
- 是鸭子类型，无需显式 `implements`，只要类型实现了接口所有方法即视为实现该接口。
- 接口底层分为 `iface`（有方法）和 `eface`（空接口 `any`）。
- 多态通过接口变量持有具体类型值，调用方法时动态分发实现。

### Q2: `error` 和 `panic` 的区别？如何优雅地处理错误？

**难度**：⭐⭐ | **频率**：🔥 高频

**考点**：错误即值、恢复机制、错误包装。

**💡 记忆关键词**：error 预期内、panic 不可恢复、%w 包装、Is/As 判断

**答案要点**：
- `error` 是普通接口，用于预期内的业务异常；`panic` 用于不可恢复的严重错误。
- 优雅处理：
  - 使用 `fmt.Errorf("context: %w", err)` 包装错误（Go 1.13+）。
  - 使用 `errors.Is()` 和 `errors.As()` 进行错误判断。
  - 避免滥用 `panic`，生产环境通常在顶层 `recover` 并记录日志。

### Q3: 如何在运行时检查变量类型？

**难度**：⭐⭐⭐ | **频率**：📌 常考
**考点**：reflect 包、类型断言、type switch、反射性能。
**答案要点**：
- **反射**：使用 `reflect.TypeOf()` 获取类型信息。
- **类型断言**：`val, ok := i.(string)`。
- **类型选择**：`switch t := v.(type) { ... }`。
- **注意**：反射有性能开销，应避免在热路径中使用。

```go
import (
    "fmt"
    "reflect"
)

var x interface{} = 42
fmt.Println(reflect.TypeOf(x))
fmt.Println(reflect.ValueOf(x).Kind())

if val, ok := x.(int); ok {
    fmt.Println("是整数:", val)
}
```

### Q4: Go 两个接口之间可以存在什么关系？

**难度**：⭐⭐⭐ | **频率**：📌 常考
**考点**：接口嵌入、接口组合、隐式实现、契约关系。
**答案要点**：
- **接口嵌入**：接口可以嵌入其他接口，形成组合关系（如 `io.ReadWriter`）。
- **实现传递**：实现子接口即自动实现所有被嵌入的父接口。
- **契约关系**：接口之间是契约组合，无继承层次。
- **空接口**：`interface{}`（或 `any`）是所有类型的超集。

```go
type Reader interface {
    Read(p []byte) (n int, err error)
}
type Writer interface {
    Write(p []byte) (n int, err error)
}
type ReadWriter interface {
    Reader
    Writer
}
```

### Q5: 值接收者与指针接收者有什么区别？方法集规则是什么？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：方法集、接口实现差异、拷贝成本、可修改性。

**💡 记忆关键词**：值方法集 T、指针方法集 *T（含 T 全部方法）、*T 能调用所有、T 不能调用 *T 方法、大结构体用指针

**答案要点**：
- **方法集规则（面试必背）**：

| 类型 | 方法集 |
|------|--------|
| `T`（值类型） | 只包含**值接收者**方法 |
| `*T`（指针类型） | 包含**值接收者 + 指针接收者**方法的全部 |

- **推论（最常考的坑）**：
  - 若方法定义在**指针接收者**上，则**只有 `*T` 能满足接口**，`T` 不满足 → 这是「编译报错 `T does not implement IFoo`」的头号原因；
  - 但 `T` 的变量调用 `*T` 的方法时，Go 会**自动取址**（`v.PtrMethod()` 等价 `(&v).PtrMethod()`），**前提是 `v` 可寻址**（map 元素、接口内的值不可寻址，会报错）。
- **选择建议**：
  - **需要修改接收者状态** → 指针接收者；
  - **结构体较大**（避免拷贝）→ 指针接收者；
  - 包含 `sync.Mutex` 等不可拷贝字段 → **必须指针接收者**（`go vet` 的 `copylock` 会报警）；
  - 小且不可变的类型（如自定义 `type Celsius float64`）→ 值接收者；
  - **同一类型的方法集保持一致**（要么全值、要么全指针），避免混用造成接口实现困惑。

```go
type Counter struct{ n int }

func (c Counter) Value() int  { return c.n }  // 值接收者：不会改原值
func (c *Counter) Inc()       { c.n++ }       // 指针接收者：改原值

type Incer interface{ Inc() }

var _ Incer = &Counter{} // ✅ *Counter 实现
// var _ Incer = Counter{} // ❌ 编译错误：Counter 的方法集不含 Inc

// 可寻址时自动取址，等价于 (&c).Inc()
c := Counter{}
c.Inc()
fmt.Println(c.Value()) // 1
```

**📝 一句话总结**：`T` 的方法集只有值方法、`*T` 含全部；只要有一个指针方法，接口实现就必须用 `*T`。

### Q6: 接口的 nil 陷阱：为什么 `err != nil` 判断会失效？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：eface/iface 双字结构、类型信息非空、返回具体类型指针引发的坑。

**💡 记忆关键词**：接口 = 类型信息 + 值，类型信息非空则接口非 nil、返回 *MyError(nil) 会「装作」非 nil

**答案要点**：
- **原理**：接口值由**两个机器字**组成 —— `(动态类型, 动态值)`。**只有当两者都为 nil（类型为 nil）时，接口才等于 nil**。
- **经典陷阱**：函数声明返回 `error`，但 `return p` 时 `p` 是 `*MyError` 类型的 nil 指针 → 接口里**类型信息是 `*MyError`（非空）**、值是 nil → `err != nil` 为 **true**，调用方以为出错了。

```go
type MyError struct{ msg string }
func (e *MyError) Error() string { return e.msg }

// ❌ 陷阱：返回了「带类型的 nil」
func bad() error {
    var p *MyError // p == nil
    return p       // 接口 = (*MyError, nil) → err != nil 成立！
}

func main() {
    if err := bad(); err != nil {
        fmt.Println("误判为错误:", err) // 输出：误判为错误: <nil>
    }
}

// ✅ 正确写法一：显式返回 nil
func good1() error {
    var p *MyError
    if p == nil {
        return nil // 直接返回无类型 nil
    }
    return p
}

// ✅ 正确写法二：避免声明为接口返回类型时返回具体类型的 nil 指针
func good2() *MyError { return nil } // 由调用方判断具体指针是否为 nil
```

- **排查手段**：打印 `fmt.Printf("%T %v\n", err, err)` —— 若输出 `*MyError <nil>` 就说明踩坑了。
- **同类坑**：`var x any = (*T)(nil)`；把 nil 的 `map`/`slice` 塞进接口（这些是**值**为 nil 但类型非 nil）。
- **工程规避**：约定「返回接口类型时只用 `return nil` 或返回非 nil 实体」，并在 CR 中列为检查项（见 5-25 Q6）。

**📝 一句话总结**：接口为 nil 需要「类型 + 值都为 nil」；返回具体类型的 nil 指针会得到「非 nil 接口」，这是 `err != nil` 失效的根因。

### Q7: `panic` / `recover` 的正确用法与边界？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：panic 语义、recover 位置、goroutine 隔离、defer 顺序。

**💡 记忆关键词**：panic 只用于不可恢复、recover 必须在同一 goroutine 的 defer 中直接调用、子 goroutine 要各自兜底

**答案要点**：
- **panic 的定位**：表示**程序无法继续运行**的错误（配置缺失、逻辑上不可能到达的分支、初始化失败）。**不要用 panic 做流程控制或业务错误处理**（业务错误用 `error`）。
- **recover 的三个硬性条件**：
  1. 必须在 **`defer` 函数中**调用；
  2. 必须**直接**调用 `recover()`（包裹在另一层函数里会失效，如 `defer func(){ helper() }()` 中的 `helper` 里 recover 无效）；
  3. **必须在同一个 goroutine 中** —— **子 goroutine panic 无法被父 goroutine 的 recover 捕获**，会导致整个进程崩溃。
- **实践模式**：
  - **HTTP 服务**：在最外层中间件 `recover`，记录堆栈返回 500（框架如 gin 自带 `Recovery`）；
  - **每个后台 goroutine / worker**：**独立 defer recover**，否则一个任务 panic 拖垮整个进程（见 2-08 Q5）；
  - **库代码**：一般**不要 recover**，让错误向上传播（除非 API 契约明确要求「绝不 panic」）；
  - `recover()` 返回的是 `any`，拿到后通常转成 error 或将 `runtime/debug.Stack()` 打进日志（**务必记堆栈，否则等于埋雷**）。

```go
// 顶层兜底（HTTP 中间件）
func recoverMW(next http.Handler) http.Handler {
    return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
        defer func() {
            if rec := recover(); rec != nil {
                slog.Error("panic recovered",
                    "err", rec,
                    "stack", string(debug.Stack()), // 一定要有堆栈
                    "path", r.URL.Path)
                http.Error(w, "internal error", http.StatusInternalServerError)
            }
        }()
        next.ServeHTTP(w, r)
    })
}

// 每个 worker 自兜底（否则整个进程挂掉）
go func() {
    defer func() {
        if rec := recover(); rec != nil {
            slog.Error("worker panic", "err", rec, "stack", string(debug.Stack()))
        }
    }()
    work()
}()
```

- **对比 error**：`error` 是**值**、可传递可包装可判定；`panic` 是**控制流中断**、跨函数传播且难以优雅恢复。**能返回 error 就返回 error**。

**📝 一句话总结**：panic 只留给不可恢复的错误；recover 必须在同 goroutine 的 defer 里直接调用，所有后台 goroutine 都要有独立兜底并记录堆栈。

### Q8: 什么是函数式选项模式（Functional Options）？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：可变参数 + 函数类型、向后兼容的 API 演进、默认值。

**💡 记忆关键词**：`func(*Config)` 选项、默认值先设、加参数不破坏调用方、优于长参数列表

**答案要点**：
- **要解决的问题**：构造函数的可选参数会爆炸（`New(host, port, timeout, retries, ...)`）；用配置结构体则无法强制默认值、调用方要写一堆零值字段。真正的新需求是**「后续加参数不破坏现有调用方」**。
- **做法**：定义 `Option = func(*Config)`，构造函数接收 `...Option`；先设默认值，再依次应用选项。

```go
type Server struct {
    addr    string
    timeout time.Duration
    maxConn int
}

type Option func(*Server)

func WithTimeout(d time.Duration) Option { return func(s *Server) { s.timeout = d } }
func WithMaxConn(n int) Option          { return func(s *Server) { s.maxConn = n } }

func NewServer(addr string, opts ...Option) *Server {
    s := &Server{addr: addr, timeout: 3 * time.Second, maxConn: 100} // 默认值
    for _, opt := range opts {
        opt(s)
    }
    return s
}

// 调用侧：可读、可扩展
srv := NewServer(":8080", WithTimeout(5*time.Second), WithMaxConn(500))
```

- **优势**：① 调用方**按需设置**、语义清晰；② **加新选项不破坏**已有调用（兼容性极佳）；③ 默认值集中在构造函数里，避免「零值陷阱」；④ 便于做参数校验（可在应用选项后统一校验）。
- **代价**：多写一些样板代码；选项本身也是公开 API，语义要一次定清楚（如 `WithTimeout(0)` 是「无超时」还是「用默认」需明确）。
- **对比**：**配置结构体 + 默认函数**（`NewServer(Config{...})`）适合配置项非常多、需要整体传递/序列化的场景；**Functional Options** 适合选项适中、追求调用可读性与兼容性，Go 生态（gRPC、zap、otel）普遍采用后者。

**📝 一句话总结**：`func(*Config)` 选项集 + 默认值 + 变参应用，做到「按需配置、加参数不破坏调用方」，是 Go 生态的主流 API 演进方案。

### Q9: 空结构体 `struct{}` 有什么用途？

**难度**：⭐⭐ | **频率**：📌 常考

**考点**：零内存占用、集合语义、信号 channel、方法集。

**💡 记忆关键词**：size 为 0、集合/去重、`chan struct{}` 发信号、不占内存

**答案要点**：
- **特点**：`unsafe.Sizeof(struct{}{}) == 0`，**不占内存**（Go 里所有零大小对象指向同一地址 `zerobase`）。
- **四种典型用途**：
  1. **集合（Set）**：`map[string]struct{}` 比 `map[string]bool` 语义更明确且省内存（值不占空间）；
  2. **信号 channel**：`chan struct{}` 只表达「事件发生」而不传数据（比 `chan bool` 更无歧义），如 `done := make(chan struct{})` 用于广播退出（见 1-03 Q2）；
  3. **方法容器**：定义只提供方法、不保存状态的类型（如无状态的 `type Handler struct{}`）；
  4. **显式忽略值**：如 `for range` 或占位，表达「此处不需要值」。
- **注意**：`map[struct{}]struct{}` 没意义（所有键相同）；不要为了省内存把需要状态的东西塞成空结构体（会失去扩展性）。

```go
// 1) Set
set := make(map[string]struct{}, 10)
set["go"] = struct{}{}
if _, ok := set["go"]; ok { /* 存在 */ }

// 2) 信号 channel（广播退出）
done := make(chan struct{})
go func() { <-done; return }()
close(done) // 一次性通知所有接收者
```

**📝 一句话总结**：`struct{}` 是「零内存的类型」，主要用来表达**集合**（map 值）与**信号**（chan struct{}）。

### Q10: Go 函数是一等公民吗？高阶函数与闭包是什么？

**难度**：⭐⭐⭐ | **频率**：📌 常考

**考点**：一等公民、函数类型、函数签名、高阶函数、闭包、自由变量捕获。

**💡 记忆关键词**：函数可作值传递、签名=参数列表+结果列表、高阶函数、闭包捕获自由变量

**答案要点**：
- **一等公民（first-class）**：函数可以**赋给变量、作为参数传入、作为结果返回、做类型判断**，和 slice/map 一样是普通值。Go 因此原生支持函数式编程。
- **函数类型与签名**：`type Printer func(contents string) (n int, err error)`。函数的**签名 = 参数列表 + 结果列表**（含顺序与类型），**参数名/结果名/函数名不算签名**。签名一致即可互相赋值。
- **函数类型是引用类型**：零值是 `nil`，调用前要判空（否则 panic）。
- **高阶函数**：满足「接收函数作参数」或「返回函数」任一即可。例：`func calculate(x, y int, op operate) (int, error)`。
- **闭包（closure）**：函数内引用了**自由变量**（既非参数/结果，也非函数内声明，而是来自外层作用域的变量）。闭包在定义时「开放」（不确定），被调用时捕获自由变量后「闭合」。
  ```go
  func genCalculator(op operate) calculateFunc {
      return func(x, y int) (int, error) { // 闭包，捕获了自由变量 op
          if op == nil { return 0, errors.New("invalid operation") }
          return op(x, y), nil
      }
  }
  ```
- **经典闭包陷阱**：循环变量捕获。Go 1.22 前 `for` 循环变量每次迭代共享，闭包里 `go func(){ use(i) }()` 会全部捕获同一个 `i` 的最终值；Go 1.22 起循环变量**每次迭代新建**，行为由 `go.mod` 的 `go` 版本决定（见 5-26）。
- **传参语义**：所有参数**按值拷贝**。数组整体拷贝（改副本不影响原值）；slice/map/channel 拷贝描述符但**共享底层**；值类型里嵌套引用类型（如 `[3][]string`）仍需小心浅拷贝。

**🔁 前端类比**：Go 函数一等公民 ≈ JS 把函数当值传（回调、高阶函数、闭包）；自由变量捕获 ≈ JS 闭包的词法作用域，连「循环变量捕获」的坑都和 JS `var` 时代一模一样。

**📝 一句话总结**：函数是普通值（签名一致即可赋值），高阶函数「传函数/返回函数」，闭包靠捕获自由变量实现逻辑的动态生成；注意按值传参与循环变量捕获陷阱。

### Q11: 如何判断具体错误值？错误处理有哪些惯用法？

**难度**：⭐⭐⭐ | **频率**：🔥 高频

**考点**：哨兵错误、错误类型、类型断言/switch、`errors.Is/As`、错误码设计。

**💡 记忆关键词**：哨兵错误判等、错误类型断言、%w+Is/As、错误码分层

**答案要点**：
- **error 是接口**（只有 `Error() string` 一个方法），`errors.New("...")` 的动态类型是包级私有的 `*errorString`；`fmt.Errorf` = `Sprintf` + `errors.New`。
- **三种判断惯用法**（按错误信息从「可知」到「未知」）：
  1. **错误类型已知范围** → 用**类型断言 / type switch**（如 `*os.PathError`、`*os.LinkError` 各自的 `Err` 字段）；
  2. **已有同类型哨兵错误值** → 直接 **`==` 判等**（如 `err == os.ErrClosed` / `os.ErrNotExist`）；
  3. **完全未知** → 只能用**错误信息字符串**判断（`os.IsExist` 内部即如此，最脆弱，慎用）。
- **哨兵错误（Sentinel Error）**：包级预定义错误值（`var ErrNotFound = errors.New("...")`），调用方直接判等。**缺点**：无法携带上下文、扩展性差、调用方会形成对特定错误的依赖。
- **错误类型（自定义 error 结构体）**：实现 `Error()`，可携带字段（路径、操作、底层 err），如 `os.PathError{Op, Path, Err}`。
- **错误包装（Go 1.13+）**：`fmt.Errorf("read file: %w", err)` 用 `%w` 保留错误链；`errors.Is(err, target)` 沿链**判等**（兼容哨兵错误），`errors.As(err, &target)` 沿链**类型匹配**。**优先 Is/As**，不要逐层 `==`。
- **工程规范（IAM 项目实践）**：设计一套**错误码体系**（业务码 + HTTP 码分离），错误在**最上层边界统一处理**（中间件把 error → 状态码/响应），**业务层只返回 error、不打日志**（避免层层打日志重复）。
- **卫述语句（Guard Clause）**：`if err != nil { return }` 前置检查，是 Go 错误处理的惯用风格，不要用 try/catch 的思维去嵌套。

**🔁 前端类比**：哨兵错误 ≈ 前端判断 `error.code === 'ECONNABORTED'`；`errors.Is/As` ≈ `error instanceof MyError` / 判断错误链上的某个类型；Go 的「错误是值」让错误携带更多结构，而非仅一条 message。

**⚠️ 常见误区**：① 用 `err.Error()` 字符串做判断（脆弱，换文案就失效）；② 不知道 `errors.Is/As`，用 `==` 直接比包装过的错误（会失效）。

**📝 一句话总结**：判断错误三种惯用法（类型断言 / 哨兵判等 / 信息字符串），工程上优先 `%w` 包装 + `errors.Is/As`，用错误码体系在边界统一处理。
