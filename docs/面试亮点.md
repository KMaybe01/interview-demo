## 二、技术难点深度剖析

### 2.1 递归动态表单引擎 ⭐⭐⭐

**位置**: `src/components/dynamic-form/` (5 核心文件 + 7 字段组件)

#### 难点分析

这是一个**完全自定义的 JSON Schema 动态表单引擎**，不依赖 @rjsf 等第三方库，从零实现递归渲染、校验、联动全流程。

**核心挑战**:
1. **无限层级嵌套**: `tabs → tab → card → form → leaf`，支持任意深度递归
2. **8 种字段类型**: string、number、select、switch、datetime、json、array
3. **条件显隐**: 字符串表达式解析 `"enableEncryption === true && certType === "ca-signed""`
4. **字段联动**: 依赖字段变化时自动计算并填充（autoFill）
5. **四重校验**: 同步校验 + 异步校验 + AJV Schema 校验 + 后端业务校验
6. **实时 JSON 编辑**: 双向绑定 — 表单编辑实时更新 JSON，JSON 编辑也可写回表单

#### 设计方案

```
┌─────────────────────────────────────────────────────────────────┐
│                    动态表单引擎架构                               │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  FormSchema (AST 树)                                            │
│    ↓                                                             │
│  Renderer.tsx (递归遍历, 深度保护, 循环引用检测)                  │

// Renderer.tsx — 递归遍历 FormSchema AST
function Renderer({ schema, data, path, onChange, ...props }: RendererProps) {
  if (schema.type === "tabs") {
    return <Tabs items={schema.tabs?.map(tab => ({
      key: tab.key,
      label: tab.title,
      children: tab.children.map(child => (
        <Renderer key={child.key} schema={child} ... />
      )),
    }))} />
  }
  if (schema.type === "card") {
    return <Card title={schema.title}>
      {schema.children?.map(child => (
        <Renderer key={child.key} schema={child} ... />
      ))}
    </Card>
  }
  if (schema.type === "leaf" && schema.properties) {
    return Object.entries(schema.properties).map(([key, leaf]) => {
      const FieldComponent = getField(leaf.type)
      return <FieldComponent key={key} schema={leaf} ... />
    })
  }
}
```

```typescript
// 字符串表达式解析 (不依赖 eval/new Function)
function evalVisible(expr: string, data: Record<string, unknown>): boolean {
  // 支持的语法: && || === !== true false 括号 数字 字符串
  const prepared = expr
    .replace(/true/g, 'true')
    .replace(/false/g, 'false')
    .replace(/&&/g, '&&')
    .replace(/\|\|/g, '||')
    .replace(/===/g, '===')
    .replace(/!==/g, '!==')
    .replace(/"([^"]+)"/g, (_, s) => `"${s}"`)
    .replace(/'([^']+)'/g, (_, s) => `"${s}"`)

  // 将变量替换为实际值
  const keys = Object.keys(data)
  const values = keys.map(k => data[k])
  try {
    return new Function(...keys, `return ${prepared}`)(...values)
  } catch {
    return true // 解析失败时默认显示
  }
}
```

#### 实时 JSON 编辑双向绑定

```typescript
// DynamicForm.tsx
export interface DynamicFormHandle {
  setFormData: (data: Record<string, unknown>) => void
}

const DynamicForm = forwardRef<DynamicFormHandle, DynamicFormProps>(function DynamicForm({
  onChange, // 数据变化时通知父组件
  ...props
}, ref) {
  const [data, setData] = useState(initialData)

  // 暴露 setFormData 给父组件 (JSON 编辑器写入)
  useImperativeHandle(ref, () => ({
    setFormData(newData) { setData(newData) },
  }), [])

  // 数据变化时实时通知
  const onChangeRef = useRef(onChange)
  onChangeRef.current = onChange
  useEffect(() => {
    if (initialized) onChangeRef.current?.(data)
  }, [data])
})
```

### 2.2 大文件断点续传 ⭐⭐⭐

**位置**: `src/pages/ChunkedUpload.tsx`

#### 难点分析

大文件上传的**断点续传**方案需要解决：网络中断恢复、暂停/恢复、并发控制、完整性校验、刷新持久化等关键问题。

#### 技术方案

```
┌─────────────────────────────────────────────────────────────────┐
│                    断点续传数据流                                  │
├─────────────────────────────────────────────────────────────────┤
│                                                                 │
│  文件选择                                                       │
│    ↓                                                             │
│  SHA-256 文件哈希 (Web Worker)                                   │
│    ↓                                                             │
│  POST /api/upload/init → uploadId + chunkSize + totalChunks     │
│    ↓                                                             │
│  并发上传分片 (滑动窗口, 最大 3)                                  │
│    ├─ 每片附带 SHA-256 分片哈希                                   │

│    └─ 失败重试 (最多 3 次, 指数退避)                              │
│    ↓                                                             │
│  POST /api/upload/complete → 服务端合并 → SHA-256 文件级验证     │
│                                                                 │

```

#### 暂停/恢复核心

```typescript
// Promise park 模式 — 暂停时阻塞上传队列
const pausedRef = useRef(false)
const parkPromiseRef = useRef<{ resolve: () => void } | null>(null)

const startUpload = async () => {
  for (const chunk of pendingChunks) {
    if (pausedRef.current) {
      // 暂停: 挂起 Promise
      await new Promise<void>((resolve) => {
        parkPromiseRef.current = { resolve }
      })
    }
    await uploadChunk(chunk) // 继续上传

**位置**: `src/utils/wsTransport.ts` + `src/pages/AlertWebSocket.tsx` + `src/stores/alertStore.ts`

#### 难点分析

WebSocket 在生产环境的可靠性是个系统工程：连接中断、重连风暴、心跳检测、背压控制、消息去重、性能节流、网络环境降级，每个环节都需精确控制。本项目将传输层抽象为独立模块 `wsTransport.ts`，实现**多协议传输层**，涵盖 4 大优化方向：

| 方向 | 策略 | 方案 |

// 自适应分区
function partition(data: number[], numChunks: number): number[][] {
  const size = Math.ceil(data.length / numChunks)
  const chunks: number[][] = []
  for (let i = 0; i < numChunks; i++) {
    chunks.push(data.slice(i * size, (i + 1) * size))

// 多路归并
function mergeSorted(...arrays: number[][]): number[] {
  const result: number[] = []
  const pointers = new Array(arrays.length).fill(0)
  while (true) {
    let minIdx = -1, minVal = Infinity
    for (let i = 0; i < arrays.length; i++) {
      if (pointers[i] < arrays[i].length && arrays[i][pointers[i]] < minVal) {
        minVal = arrays[i][pointers[i]]
        minIdx = i
      }
    }
    if (minIdx === -1) break
    result.push(minVal)
    pointers[minIdx]++
  }
  return result
}

function findNode(tree: TreeNode[], key: string): TreeNode | null {
  for (const node of tree) {
    if (node.key === key) return node
    if (node.children) {
      const found = findNode(node.children, key)
      if (found) return found
    }
  }
  return null
}

      ...node,
      children: node.children ? removeNode(node.children, key) : [],
    }))
}

### 2.11 LRU 路由缓存 ⭐⭐

**位置**: `src/pages/LruRouteCache.tsx` + `src/utils/lru.ts` + `src/stores/lruRouteStore.ts`

#### 难点分析

Tab 切换时保持页面状态，同时限制最大缓存数量避免内存溢出。此外还需解决**缓存一致性问题**：A 页面修改数据后，B 缓存页面如何同步更新？

#### 设计方案

```typescript
class LRUCache<K, V> {
  private capacity: number
  private cache = new Map<K, { value: V; count: number }>()

  get(key: K): V | undefined {
    const entry = this.cache.get(key)
    if (!entry) return undefined
    entry.count++            // 增加访问计数
    this.cache.delete(key)   // 删除重新插入以提升优先级
    this.cache.set(key, entry)
    return entry.value
  }

  put(key: K, value: V): void {
    if (this.cache.size >= this.capacity) {
      // 淘汰访问计数最低的
      let minCount = Infinity, minKey: K | null = null
      for (const [k, v] of this.cache) {
        if (v.count < minCount) {
          minCount = v.count
          minKey = k
        }
      }
      if (minKey !== null) this.cache.delete(minKey)
    }
    this.cache.set(key, { value, count: 0 })
  }
}
```

**页面缓存策略**: DOM display:none 保持状态，而非卸载组件。切换回时直接从缓存读取，不重新挂载。

### 4.1 forwardRef + useImperativeHandle

**应用场景**: DynamicForm 暴露 setFormData 给父组件

const DynamicForm = forwardRef<DynamicFormHandle, DynamicFormProps>(function DynamicForm(props, ref) {

async function uploadChunk(chunk) {

// 模式 2：generation 计数器（WebSocket 等跨生命周期场景）
const genRef = useRef(0)
const connect = () => {
  const gen = ++genRef.current
  ws.onmessage = (e) => {
    if (gen !== genRef.current) return // 过期连接，丢弃
    handleMessage(e)
  }
}
```

**应用范围**：WebSocket 回调、分片上传进度、表单 onChange 通知，共 10+ 处。

## 八、面试高频问题（深度版）

### 8.1 React 核心概念

#### Q1: forwardRef + useImperativeHandle 解决了什么问题？

**答**:

```
React 默认是单向数据流（props 父→子传递）。
当子组件内部状态需要被父组件操作时，需要 forwardRef + useImperativeHandle。

本项目应用:
├─ DynamicForm 管理内部 data 状态 (useState)
├─ 父组件 JsonSchemaForm 需要写回 JSON 编辑结果
├─ DynamicForm 通过 forwardRef 暴露 setFormData
└─ 父组件调用 formRef.current.setFormData(parsed)

不这样做会怎样?
├─ 方案1: 将所有状态提升到父组件 → DynamicForm 不再是可控的自洽组件
├─ 方案2: 使用全局状态 (Zustand) → 过度设计
└─ 方案3: 使用关键属性强制 remount → hack 做法，丢失中间状态
```

#### Q2: useRef 和 useState 的本质区别？项目中如何应用？

**答**:

| 特性 | useState | useRef |
|------|----------|--------|
| 触发重渲染 | ✅ 是 | ❌ 否 |
| 值可变性 | 需要 setState | .current 直接修改 |
| 适用场景 | 需要 UI 更新的状态 | 不需要 UI 更新的持久化数据 |
| 记忆性 | 每次渲染都是新值 | 跨渲染保持引用 |

**本项目应用**:
```typescript
// 1. wsRef — WebSocket 实例 (不触发重渲染)
const wsRef = useRef<WebSocket | null>(null)

// 2. genRef — generation 计数器 (跨渲染保持)
const genRef = useRef(0)

// 3. pausedRef — 暂停标志 (命令式控制)
const pausedRef = useRef(false)

// 4. onChangeRef — 最新回调持有 (闭包陷阱修复)
const onChangeRef = useRef(onChange)
onChangeRef.current = onChange

// 5. data — 表单数据 (触发 UI 更新)
const [data, setData] = useState(initialData)
```

#### Q3: React 闭包陷阱产生的原因？项目中如何修复？

**答**:

```
产生原因:
├─ React 函数组件每次渲染都创建新的闭包
├─ useEffect / useCallback 捕获的是创建时的 state 值
└─ 异步回调 (setTimeout / Promise / WebSocket onmessage) 执行时 state 已过期

项目修复模式:
├─ onUpdateRef.current 模式
│   └─ 每次渲染更新 ref，异步回调通过 ref 读取最新值
├─ generation 计数器 (genRef)
│   └─ 每次操作递增，回调检查 genRef.current 是否匹配
└─ 稳定 key / effect 依赖最小化
    └─ 避免 key 变化导致组件卸载，effect 只依赖必要变量
```

### 8.2 动态表单引擎

#### Q1: 什么是递归渲染引擎？如何避免性能问题？

**答**:

```
递归渲染引擎 = 将 JSON Schema (AST 树) 递归解析为 React 组件树

渲染流程: renderTabs → renderCard → renderForm → renderLeaf

性能保障:
├─ React 19 自动 memo: 编译器自动推断依赖，props 不变时跳过重渲染
├─ 分层隔离: tabs/card/form/leaf 四层天然隔离，一层变化不影响兄弟层级
└─ 深度保护: _depth / maxDepth 防止无限递归，循环引用检测 _visitedRefs
```

#### Q2: 为什么选择自定义表单引擎而不是 @rjsf？

**答**:

```
选型考量:
├─ @rjsf 优势: 开箱即用，社区成熟
├─ @rjsf 劣势:
│   ├─ 扩展复杂: 自定义控件需要了解 rjsf 的 Widget/Field 体系
│   ├─ 样式限制: 受限于 rjsf 的模板结构，定制成本高
│   └─ 灵活性不足: 条件显隐表达式、字段联动、异步校验需要额外工作
├─ 自定义引擎优势:
│   ├─ 完全可控: 渲染流程、校验逻辑、联动机制都由自己控制
│   ├─ 轻量无依赖: 不引入第三方表单库
│   └─ 可扩展: registry 注册新字段类型只需一行 registerField()
│
└─ 面试价值: 展示架构设计能力，而非 "会用库"
```

### 8.3 WebSocket vs SSE 选型

#### Q1: 什么时候用 SSE，什么时候用 WebSocket？

**答**:

```
├─ SSE (Server-Sent Events):
│   ├─ 单向推送（服务端 → 客户端）
│   ├─ 基于 HTTP，浏览器原生 EventSource 支持自动重连
│   ├─ 代码量少 (~20 行 vs WebSocket ~80 行)
│   └─ 适合：日志流、通知推送、状态更新
│
├─ WebSocket:
│   ├─ 双向通信（客户端 ↔ 服务端）
│   ├─ 需要心跳维持、消息去重、重连策略、背压控制
│   └─ 适合：实时告警、聊天、协同编辑
│
└─ 本项目: 日志流用 SSE（单向足够），告警用 WebSocket（需要双向），
   但 WebSocket 不可用时自动降级为 SSE / Polling，保证不中断
```

### 8.4 Zustand vs Redux vs Context

#### Q1: 为什么选 Zustand 而不是 Redux 或 Context？

**答**:

```
├─ Zustand:
│   ├─ 轻量（~1KB），无 boilerplate
│   ├─ 内置持久化中间件 (persist)
│   ├─ 按 selector 订阅，不触发无关组件重渲染
│   └─ 适合: 中小型应用、持久化需求
│
├─ Redux:
│   ├─ 生态丰富，中间件体系成熟
│   ├─ 模板代码多（action/reducer/slice）
│   └─ 适合: 大型项目、复杂状态逻辑
│
├─ Context:
│   ├─ React 内置，无额外依赖
│   ├─ 频繁更新时性能不佳（全子树重渲染）
│   └─ 适合: 全局主题/语言/用户信息

本项目选择 Zustand 的原因:
├─ 上传状态需要 localStorage 持久化 → Zustand persist 内置
├─ 状态结构简单（文件列表 + 分片状态）→ 不需要 Redux 复杂度
└─ 性能要求高 → Zustand 按 selector 订阅
```

### 8.5 大文件断点续传

#### Q1: 为什么分片上传而不是直接上传？

**答**:

```
分片上传优势:
├─ 断点续传: 失败后从失败分片重传，而非整个文件
├─ 并发控制: 可调节并发数，避免单连接占满带宽
└─ 进度精确: 实时追踪每分片的上传状态

直接上传劣势:
├─ 失败后必须重新上传整个文件
├─ 大文件占用大量内存
└─ 无进度反馈，用户体验差
```

#### Q2: 暂停后刷新页面，如何恢复上传？

**答**:

```
恢复流程:
├─ 页面加载 → loadFromStorage() 从 localStorage 恢复文件列表
├─ useEffect 检查未完成的上传 → GET /api/upload/status/:uploadId
├─ 服务端返回已接收分片列表 → 前端标记对应分片为 "done"
├─ 用户拖入相同文件 → 检测到已有未完成记录 → 显示"续传"按钮
└─ 点击续传 → 跳过 done 分片，仅上传 missing 分片
```

### 场景 1：GIS 十万级点位

**Q：十万级点位渲染你是怎么优化的？**

```
四重优化策略:
├─ Cluster 聚合: 低 Zoom 聚合为聚类点 → 数据量 100,000 → 50
├─ BBOX 视口裁剪: 只渲染视口内的点位
├─ dataCache 全量缓存: 平移缩放无需重新请求
└─ moveend 惰性刷新: 拖动结束时才触发重绘
最终帧率: <10fps → 60fps
```

### 场景 2：WebSocket 重连与协议降级

**Q：指数退避 + jitter 为什么重要？**

```
├─ 纯指数退避: 所有客户端同时重连 → 服务端压力尖峰
├─ +jitter: 随机分散重连时间 → 平滑服务端负载
└─ 公式: base = min(1000 * 2^attempt, 30000); jitter = base * (0.8 + random() * 0.4)
```

**Q：为什么要做 WebSocket → SSE → Polling 的三级降级？**

```
├─ 企业内网环境: WebSocket 可能被代理/Nginx 阻止或超时断开
├─ SSE (EventSource): 基于 HTTP 长连接，兼容性更好，浏览器自动重连
├─ Polling: 最后保底方案，所有网络环境都支持
├─ 降级策略: WebSocket 重试 MAX_RETRY(10) 次失败 → SSE → Polling
├─ UI 提示: 橙色 Tag 标示当前传输类型（"SSE 降级" / "轮询降级"）
└─ 面试价值: 展示端到端可靠性设计思维，而非仅关注 WebSocket 本身
```

**Q：背压控制和消息合并解决了什么问题？**

```
├─ 背压问题: WebSocket.bufferedAmount 持续增长 → 内存溢出、延迟增加
├─ 背压方案: >1MB 排队等待，<256KB 恢复发送，raf 驱动 drain 循环
├─ 消息合并: 16ms 延迟或 64KB 上限触发 flush
├─ 效果: 降低网络包数量 10~50 倍，避免发送端压倒接收端
└─ 面试价值: 展示对网络传输底层机制的理解

### 场景 3：双 Token 无感刷新

**Q：Refresh Token Rotation 是什么？为什么需要？**

```
Refresh Token Rotation:
├─ 每次刷新 Access Token 时，同时颁发新的 Refresh Token
├─ 旧 Refresh Token 立即失效（标记为已用）
├─ 防止重放攻击: 即使 Refresh Token 泄露，也只能使用一次
└─ 本项目: 服务端维护 usedTokens 列表，检测到重复使用即告警
```

### 场景 4：React 闭包陷阱

**Q：WebSocket 回调中的闭包陷阱是怎么修复的？**

```
修复模式:
├─ generation 计数器: genRef 每次连接递增
├─ 回调检查 genRef.current === gen，不匹配则丢弃
├─ 避免过期回调污染新连接的数据
└─ 通用方案: 所有异步回调 + 跨生命周期操作都建议使用 generation 模式
```

### 场景 5：表单引擎 vs @rjsf

**Q：你觉得自定义表单引擎比 @rjsf 好在哪？**

```
├─ @rjsf 是通用方案，适合快速搭建
├─ 自定义引擎:
│   ├─ 完全控制渲染流程（tabs/card/form 的自定义布局）
│   ├─ 灵活的条件显隐（字符串表达式，运行时解析）
│   ├─ 完备的校验体系（同步/异步/AJV/后端四级）
│   ├─ 实时 JSON 编辑双向绑定
│   └─ 自定义字段只需 registerField() 一行代码
└─ 面试场景下，自定义引擎更能展示架构设计能力
```
