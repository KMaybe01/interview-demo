### 难点 1：大文件断点续传 — ChunkedUpload

```
🔍 亮点：
  基于 SHA-256 分片哈希 + Zustand 持久化 + 服务端 session 的断点续传方案
  支持暂停/恢复/停止 + 刷新后自动恢复 + 多分片并发上传

💪 能力突出：
├─ 状态持久化：Zustand store + localStorage 双重持久化，页面刷新不丢失
├─ 服务端协同：服务端 JSON 文件持久化 session + 状态查询 API 恢复进度
├─ 并发控制：滑动窗口限制最大并发分片数（可配置 1-10），避免 OOM

🛠 难点解决：
├─ 完整性校验：每分片 SHA-256 哈希 + 最终文件级 SHA-256 双校验
├─ 暂停/恢复：AbortController + pausedRef parked Promise 模式
│   └─ 暂停时 in-flight 分片自然完成，未开始的分片被 Promise 阻塞
│   └─ 恢复时 resolve parked Promise，继续消费分片队列
├─ 闭包陷阱：上传过程中的状态回调用 useRef 持有最新回调避免过期
│   └─ onUpdateRef.current 模式修复 React 闭包捕获旧状态的问题
├─ 断点恢复：服务端 GET /api/upload/status/:uploadId 返回已接收分片列表
│   └─ 前端仅上传缺失分片，避免重复传输
├─ 错误重试：单分片最多 3 次重试 + 指数退避（1s/2s/3s）
│   └─ 超过重试次数标记分片失败，提供"重试"按钮重置全部 pending
└─ 组件稳定性：修复 id 变更导致组件卸载 / status 变化导致 effect 回路 / 暂停后 resume 重复启动等连锁 bug

📈 项目收获：
├─ 深入理解"断点续传"的全链路设计：前端分片 → 后端 session → 服务端合并
├─ 掌握了 React 闭包陷阱的修复模式：ref 持有回调 / 稳定 key / effect 依赖管理
└─ 暂停/恢复的 Promise park 模式是一种通用异步中断模式，可用于文件上传/数据同步/批处理等场景
```

#### 追问链：大文件断点续传

**Q1：为什么分片上传而不是直接上传？**

```
分片上传 vs 直接上传：
├─ 分片上传优势：
│   ├─ 断点续传：失败后从失败分片重传，而非整个文件
│   ├─ 并发控制：可调节并发数，避免单连接占满带宽
│   └─ 进度精确：实时追踪每分片的上传状态
├─ 直接上传劣势：
│   ├─ 失败后必须重新上传整个文件
│   ├─ 大文件占用大量内存
│   └─ 无进度反馈，用户体验差
└─ 适用场景：>100MB 文件、弱网环境、需要断点续传的场景
```

**Q2：SHA-256 完整性校验是怎么实现的？**

```
双层 SHA-256 校验：
├─ 分片级：每分片上传前计算 SHA-256，服务端验证后存储
│   └─ 防止传输过程中数据损坏
├─ 文件级：所有分片合并后，服务端计算完整文件 SHA-256
│   └─ 与前端 computedFileHash 对比，确保合并结果正确
└─ 实现细节：Web Crypto API crypto.subtle.digest 在 Web Worker 外执行
    └─ 大文件哈希计算可能卡顿，可优化为 Web Worker 执行
```

**Q3：暂停后刷新页面，如何恢复上传？**

```
恢复流程：
├─ 页面加载 → loadFromStorage() 从 localStorage 恢复文件列表
├─ useEffect 检查未完成的上传 → GET /api/upload/status/:uploadId
├─ 服务端返回已接收分片列表 → 前端标记对应分片为 "done"
├─ 用户拖入相同文件 → 检测到已有未完成记录 → 显示"续传"按钮
└─ 点击续传 → 跳过 done 分片，仅上传 missing 分片
```

### 难点 2：WebSocket 告警推送 — AlertWebSocket

```
🔍 亮点：
  全功能 WebSocket 客户端：指数退避重连 + 心跳 Ping/Pong + 消息去重 + RAF 节流
  ECharts 实时趋势图 + 连接中断控制 + 丢段检测

💪 能力突出：
├─ 连接可靠性：指数退避 + jitter（随机抖动）避免重连风暴
├─ 消息节流：双缓冲 + requestAnimationFrame 驱动，每帧批量处理一次
├─ 去重机制：seenRef Set 存储已处理消息 ID，上限 5000 自动回收

🛠 难点解决：
├─ 重连风暴防护：jitter 算法 base * (0.8 + Math.random() * 0.4)
│   └─ 多个客户端同时断开时，重连时间随机分布，避免服务端瞬间压力
├─ 心跳自愈：30s Ping / 10s Pong 超时
│   └─ 超时后主动关闭 WebSocket → 触发 onclose → 自动重连
│   └─ 避免"僵尸连接"——TCP 存活但服务器不响应
├─ 并发安全：generation 计数器（genRef）防止过期回调污染新连接
│   └─ 每次 connect() 递增 gen，回调检查 genRef.current !== gen 则丢弃
├─ 中断控制：手动断开/暂停/恢复
│   └─ pausedRef / manualStopRef 控制 onclose 是否自动重连
│   └─ 暂停时停止 ECharts RAF 循环，恢复时重启
├─ 丢段检测：服务端 seq 序号 + 前端 lastSeq 对比
│   └─ 检测到 seq 跳跃 => gapsDetected++，UI 展示"丢段"标签
└─ 服务端消息积压：chan 缓冲区满时 default case 丢弃
    └─ 前端无感知，靠丢段检测发现数据不完整

📈 项目收获：
├─ WebSocket 在生产环境中的可靠性是个系统工程，不仅仅是连接/断开的简单处理
├─ 重连策略、心跳机制、消息去重、缓冲节流四者缺一不可
└─ generation counter 模式是处理异步回调竞争条件的通用方案
```

#### 追问链：WebSocket

**Q1：指数退避 + jitter 为什么重要？**

```
├─ 纯指数退避：所有客户端在同一时间点重连 → 服务端压力尖峰
├─ +jitter：随机分散重连时间 → 平滑服务端负载
└─ 公式：base = min(1000 * 2^attempt, 30000); jitter = base * (0.8 + random() * 0.4)
    └─ 范围：800ms ~ 42s，maxRetry = 10
```

**Q2：RAF double-buffer 模式解决了什么问题？**

```
├─ 问题：WebSocket onmessage 每帧可能触发数百次，直接 setState 导致性能下降
├─ 解决：onmessage 只 push 到 bufferRef（轻量操作）
│   └─ RAF 循环每帧 drain 一次 buffer，批量处理 + 去重 + 排序 + setState
├─ 优势：合并多次微任务为一次宏任务，减少渲染次数
└─ 适用场景：高频率状态更新（实时告警/日志流/图表数据）
```

### 难点 3：Web Worker 分治有序合并

```
🔍 亮点：
  Worker Pool + 自适应分区 + 有序归并缓冲区 + 主线程对比
  大数组分片并行排序，自适应分区策略避免小文件调度开销

💪 能力突出：
├─ 并行计算：将排序任务拆分为 N 个独立分区，Worker Pool 并行执行
├─ 算法工程化：自适应的分治策略——大文件多分片、小文件少分片
└─ 正确性验证：主线程 Array.sort 结果对比，自动校验 Worker 排序正确性

🛠 难点解决：
├─ Worker Pool 管理：固定数量 Worker（通常 navigator.hardwareConcurrency）
│   └─ 任务队列 + Promise 包装，Worker 空闲时自动领取下一个任务
├─ 自适应分区：min(分区数, Worker 数 + 1)，避免分区过多调度开销
│   └─ dataSize / Worker 数 计算分区大小，确保负载均衡
├─ 有序归并：多路归并算法，每次从所有分区取最小元素
│   └─ 优先队列优化归并效率（可进一步优化为堆排序）
└─ 对比验证：Worker 结果与主线程结果逐元素对比
    └─ 定位不一致区间，确保排序正确

📈 项目收获：
├─ 分治 + 并行是突破 JavaScript 单线程瓶颈的核心模式
├─ Worker Pool 设计要平衡"并行度"和"调度开销"
└─ 合理利用 hardwareConcurrency，在不同设备上自适应
```

### 难点 4：大文件断点续传 — 连锁 Bug 修复

```
🔍 亮点：
  从"功能实现"到"稳定运行"的 Bug 修复全记录
  4 个连锁 Bug 的根因分析与修复策略

💪 能力突出：
├─ 根因分析能力：不满足于"能用了"，追问"为什么这里会出问题"
├─ React 闭包原理：理解 useCallback 依赖、闭包捕获、effect 清理机制
└─ 调试方法：console.trace + 打断点 + stack trace 逐帧分析

🛠 难点解决：
├─ Bug 1：useEffect 依赖 status 变化引起 uploadOne 静默停止
│   └─ 根因：status 从 "uploading" 变 "hashing" → 组件卸载 → 上传终止
│   └─ 修复：移除不必要的状态变更，保持稳定 key
├─ Bug 2：onUpdate({ id }) 修改 id 字段 → React key 变化 → 组件卸载
│   └─ 根因：React 使用 key 标识组件，id 变化导致旧组件卸载新组件挂载
│   └─ 修复：新增 uploadId 字段，id 保持首次生成值不变
├─ Bug 3：闭包捕获过期 item.id → updateFile 找不到目标文件
│   └─ 根因：useCallback 闭包捕获了旧 files 引用
│   └─ 修复：onUpdateRef.current = useCallback(...)，upload loop 用 ref 调用
├─ Bug 4：暂停后 resume 调用 startUpload → 重复创建上传任务
│   └─ 根因：resume 和 startUpload 复用同一入口函数
│   └─ 修复：resume 只释放 pausedRef lock，不重新执行 startUpload 流程

📈 项目收获：
├─ React 的"声明式"模式在"命令式"异步操作中容易出现隐蔽 Bug
├─ 核心原则：key 保持稳定 / effect 依赖最小化 / 异步回调用 ref 传递
└─ 这 4 个 Bug 展示了 React 闭包陷阱的常见模式，值得深入理解
```

### 场景 1：GIS 十万级点位

**Q：十万级点位渲染你是怎么优化的？**

```
四重优化策略：
├─ Cluster 聚合：低 Zoom 聚合为聚类点，高 Zoom 展开为独立点位
│   └─ 数据量从 10,000 → 50，下降 200 倍
├─ BBOX 视口裁剪：只渲染当前视口内的点位
│   └─ 用户平移时才触发新数据加载
├─ dataCache 全量缓存：所有点位数据一次性缓存到内存
│   └─ 平移/缩放无需重新请求服务端
└─ moveend 惰性刷新：拖动结束时才触发重绘
    └─ RAF 节流，每帧最多重绘一次
```

### 场景 2：SSE vs WebSocket

**Q：什么时候用 SSE，什么时候用 WebSocket？**

```
├─ SSE：
│   ├─ 单向推送（服务端 → 客户端）
│   ├─ 基于 HTTP，天然支持断线重连（EventSource）
│   ├─ 适合：日志流、通知推送、状态更新
│   └─ 本项目：SSE 日志流
├─ WebSocket：
│   ├─ 双向通信（客户端 ↔ 服务端）
│   ├─ 需要心跳维持、onmessage 处理
│   ├─ 适合：实时告警、聊天、协同编辑
│   └─ 本项目：WebSocket 告警推送
└─ 选择原则：单向用 SSE（更简单），双向用 WebSocket（更灵活）
```

### 场景 3：Zustand vs Redux vs Context

**Q：为什么选 Zustand 而不是 Redux 或 Context？**

```
选型考量：
├─ Zustand：
│   ├─ 轻量（~1KB），无 boilerplate
│   ├─ 内置持久化中间件（subscribe + getState）
│   ├─ TypeScript 类型推断优秀
│   └─ 适合：中小型应用、持久化需求
├─ Redux：
│   ├─ 生态丰富，中间件体系成熟
│   ├─ 模板代码多（action/reducer/slice）
│   └─ 适合：大型项目、复杂状态逻辑
├─ Context：
│   ├─ React 内置，无额外依赖
│   ├─ 频繁更新时性能不佳（全子树重渲染）
│   └─ 适合：全局主题/语言/用户信息

本项目选择 Zustand 的原因：
├─ 上传状态需要 localStorage 持久化 → Zustand 内置
├─ 状态结构简单（文件列表 + 分片状态）→ 不需要 Redux 的复杂度
└─ 性能要求高 → Zustand 按 selector 订阅，不触发无关组件重渲染
```

### 场景 4：动态表单引擎

**Q：动态表单的递归渲染是如何避免性能问题的？**

```
性能保障策略：
├─ React 19 自动 memo：React 19 编译器自动推断组件依赖，无需手动 React.memo
│   └─ 编译期自动为组件添加 memo 包装，props 不变时跳过重渲染
├─ 分层渲染：tabs/card/form/leaf 四层天然隔离
│   └─ 一层输入变化不影响兄弟层级，React 19 自动跳过未变化子树
└─ 虚拟滚动：深层嵌套时只渲染可见部分（react-window）
```

> React 19 内置编译优化，`React.memo` / `useMemo` / `useCallback` 大多不再需要手动编写，编译器自动推导组件的输入依赖，仅在依赖变化时重渲染 — 这与 Vue 3 的模板编译优化异曲同工，但 React 的实现更通用（不依赖模板）。
